# Betrieb einer Instanz

Wie Frieda auf einem eigenen Server läuft: Seiten ausliefern, Rückmeldungen annehmen, was der AI-Client über den Konnektor festlegt sofort ins Reisen-Repo schreiben, veröffentlichen, neue Reisen freischalten und an Fristen erinnern. Alles dafür liegt in dieser Software unter `betrieb/`. Eine Instanz liefert nur ihre Werte. Frieda enthält keine eigene KI (ADR-0001): Auf dem Server läuft kein Claude Code; bis zum 29.10.2026 gab es einen Einarbeiten-Lauf, der Eingaben mit `claude -p` einarbeitete (Paket D), er ist mit Paket O-3 entfallen.

## Instanz

Eine **Instanz** ist eine Reisegruppe mit eigenem Betreiber: Ordner, Dienste und Adresse auf einem Server, gebaut aus einem Klon dieser Software (#454; vorher aus einem Reisen-Repo, Abschnitt „Umzug auf den Software-Klon“). Mehrere Gruppen bedeuten mehrere Instanzen, gern auf demselben Server. Die Reisen einer Instanz teilen sich Ablage, Dienste und Meldeweg; getrennt sind die Gruppen nur über eigene Instanzen. Mandanten innerhalb einer Instanz sind ein späterer Schritt (Issue #68).

| Teil | Ort | Inhalt |
|---|---|---|
| Software | dieses Repo | Generator, Dienste, `betrieb/` mit Skripten und Vorlagen |
| Bauordner | Software-Klon `<FR_SEITEN>/_software` auf dem Server (#454), öffentlich und ohne Anmeldung geholt, spiegelt nur `main` (`FR_WURZEL` der Units) | von hier wird gebaut, hier laufen Timer und Dienste; nie darin arbeiten (Abschnitt „Bauordner und Arbeitsordner“) |
| Ort der Instanz | `<FR_DIENST>/instanz/`: `einstellungen.env`, `melden.sh` (Meldeweg), optional `tests/` | Einstellungen und Meldeweg der Instanz, vom Server-Backup erfasst, unabhängig vom Klon |
| Python der Dienste | `<FR_DIENST>/python` | Umgebung außerhalb des Klons; bei geänderter `engine/requirements.txt` daneben neu gebaut (`python.neu`), nach grüner Prüfung getauscht, die vorige bleibt als `python.alt` |
| Letzter guter Stand | `<FR_DIENST>/software-gut` | Commit der Software, mit dem der letzte Lauf ganz grün war; Rückfall bei einem gescheiterten Deploy |
| Reisen-Repo (alt) | eigenes, privates Repo mit der Software als Submodul `frieda/` | bis zum Umzug Bauordner und Ort von `betrieb/einstellungen.env`, Meldeskript und `tests/`; danach Archiv, der alte Bauordner bleibt als Rückweg liegen |
| Arbeitsordner | eigener Klon dieser Software, Branches erlaubt | hier wird gearbeitet, über Pull Requests nach `main` |
| Arbeitskopie des Schreibwegs | `<Bauordner>-schreiben-<reise>` | Git-Worktree je Reise, legt der Dienst selbst an |
| Seiten | `<FR_SEITEN>/<reise>/` | gebaute Seiten, nginx liefert sie aus |
| Ablage | `<FR_ABLAGE>/<reise>/` (`eingang.jsonl`, `status.json`, `aufgaben.json`, `brett.json`, `packstand.json` (Packliste, ADR-0010), …) | Eingaben der Mitreisenden; nie im Repo |
| Konten | `<FR_KONTEN>/` (`konten.db`, Dienst-Geheimnis, `sicherung/konten.db`, `neu/` mit Anfragen nach neuen Reisen und Meldungen an Personen) | Konten, Anmeldungen, Einladungen und alles Personenbezogene ohne Reise; nie im Repo, nie in einer Reise |
| Reisespeicher | `<FR_SPEICHER>/` (`reisen.db`, `sicherung/reisen.db`; Vorgabe `<FR_SEITEN>/_speicher`) | Reisedaten als unveränderliche Versionen in SQLite (`engine/reisespeicher.py`, [ADR-0009](adr/0009-reisespeicher.md), #346); ab Stufe 2 (#347) schreibt der Schreibweg die Reisen aus `FR_SPEICHERREISEN` hinein (Speicherweg), alle anderen bis Stufe 5 über Git |
| Dienstordner | `<FR_DIENST>/` | Code der Dienste, Stände, Stempel, vorgemerkte Links, geheime Einstellungen |
| Ordner des Konnektors | `<FR_KONNEKTOR>/seiten.json` (600), `neue-reisen-ausstehend.jsonl` | Links zu den Seiten, vorgemerkte neue Reisen; nie im Repo (die Datei `zugaenge.json` der alten Links ist abgeschafft, #421, und kann weg) |
| systemd | `<instanz>-rueckmeldungen`, `-konnektor`, `-schreiben`, `-push`, `-veroeffentlichen.timer`, `-waechter.timer` | aus `betrieb/vorlagen/`, erzeugt von `einrichten.sh` |
| nginx | `<FR_NGINX_SNIPPETS>/<instanz>-<reise>.conf` (mit Token), `<instanz>-konnektor-orte.inc` mit `<instanz>-konnektor.inc`, Zone in `conf.d/<instanz>-zone.conf` | aus `betrieb/vorlagen/` |

Die Skripte rufen sich im Software-Klon als `betrieb/<skript>.sh` auf, mit `FR_WURZEL=<FR_SEITEN>/_software` (vor dem Umzug im Reisen-Repo als `frieda/betrieb/<skript>.sh`).

## Was wohin gehört

Drei Gruppen, die sich nie mischen sollen:

1. **Die Software** (dieses Repo): Code, Vorlagen, Werkzeuge. Auf dem Server liegt eine Kopie des Dienst-Codes in `<FR_DIENST>/*.py`, die `deploy.sh` anlegt. Sie ist für jede Instanz gleich und enthält nichts Eigenes.
2. **Die Daten einer Reisegruppe** (das Reisen-Repo und seine Ordner): Reisen, Seiten, Ablage mit Rückmeldungen, Aufträgen, Aufgaben und Belegen, Einstellungen und Meldeweg der Instanz.
3. **Daten der Nutzer**: Konten und Anmeldungen (`<FR_KONTEN>/`), Ordner des Konnektors (`<FR_KONNEKTOR>/`), Anfragen nach neuen Reisen samt Meldungen an Personen (`<FR_KONTEN>/neu/`, Rechte 700) und der Mailzugang (`konten.env`). Sie gehören nicht in das Reisen-Repo und gehören nicht einer einzelnen Reise. Betriebsdaten des Konnektors bleiben in `<FR_KONNEKTOR>/` (`seiten.json`, `neue-reisen-ausstehend.jsonl`; `zugaenge.json` ist mit den alten Links entfallen, #43, #421).

**Sicherung:** Das Server-Backup sichert `<FR_KONTEN>/` und `<FR_ABLAGE>/`. Die Reisen selbst liegen im Reisen-Repo, die Seiten entstehen daraus neu. `konten.db` läuft im WAL-Modus; eine Kopie der Datei im laufenden Betrieb kann unbrauchbar sein. Darum schreibt der Wächter-Lauf täglich einen sauberen Schnappschuss über die Backup-API von SQLite nach `<FR_KONTEN>/sicherung/konten.db` (`engine/konten.py sichern`, geprüft mit `integrity_check`, ohne WAL-Dateien). Zurückholen: Dienste anhalten, den Schnappschuss als `<FR_KONTEN>/konten.db` einsetzen (alte `-wal`/`-shm` entfernen), Dienste starten.

**Reisespeicher (#346, [ADR-0009](adr/0009-reisespeicher.md)):** `<FR_SPEICHER>/reisen.db` hält die Reisedaten als Versionen, nur anhängen (Ordner 700, Datei 600, WAL). Der Wächter-Lauf schreibt täglich einen Schnappschuss nach `<FR_SPEICHER>/sicherung/reisen.db` (`engine/reisespeicher.py sichern`, wie bei den Konten über die Backup-API, geprüft mit `integrity_check`, ohne WAL-Dateien); scheitert ein Schnappschuss, bleibt die letzte gute Sicherung stehen. Das Wegbringen außer Haus ist Sache des Server-Backups der Instanz; es ruft unmittelbar vor dem Archivieren `betrieb/sichern.sh` auf (als Betriebsbenutzer, `FR_WURZEL` = Bauordner; schreibt beide Schnappschüsse frisch, Exit 1, wenn einer scheitert, dann kein Heartbeat des Backups; #506), sonst wäre der Schnappschuss im Backup bis zu einem Tag älter als das Backup selbst. Es muss `<FR_SPEICHER>/sicherung/` mitsichern, spätestens sobald der Schreibweg in den Speicher schreibt (Stufe 2, #347); bis dahin ist der Speicher nur eine Kopie. Zurückholen: Schreiber anhalten, den Schnappschuss als `<FR_SPEICHER>/reisen.db` einsetzen (alte `-wal`/`-shm` entfernen), dann `engine/reisespeicher.py pruefen` (muss `ok` melden) und zur Kontrolle eine Reise mit `engine/reisespeicher.py exportieren <reise> <leerer Ordner>` ausgeben und mit dem erwarteten Stand vergleichen. Weitere Befehle: `importieren <ordner> <reise> <wer> [--grund TEXT] [--ab N]`, `verlauf <reise> [n]`, `exportieren <reise> <ziel> [--bis N]` (auch ein alter Stand), `zuruecksetzen <reise> <bis> <wer> <grund>` (ein neuer Vorgang, der Verlauf bleibt). Der Schutz gegen Ändern und Löschen hält Software-Fehler und Fehlbedienung ab, nicht jemanden mit Schreibzugriff auf die Datei; `pruefen` rechnet deshalb alle Prüfsummen nach.

**Ablage der Medien (Stufe 4, #349):** Fotos, GPX-Dateien und Grundkarten einer Speicher-Reise (Dateien unter `medien/` mit der Endung png, jpg, jpeg, webp, gif, gpx oder pmtiles; ohne `medien/icon.svg` und `medien/icon.png`) liegen nicht in der Datenbank, sondern einmal je Inhalt in `<FR_SPEICHER>/ablage/<aa>/<prüfsumme>` (Ordner 700, Dateien 400); die Datenbank hält nur den Verweis mit der Prüfsumme. Die Ablage wird nur ergänzt: Die Software ändert keine Datei darin und löscht nur beim endgültigen Entfernen einer gelöschten Reise die Dateien, auf die keine andere Reise mehr verweist (#381); verwaiste Dateien (ein Vorgang scheiterte nach dem Ablegen) sind harmlos und werden nur vom Betreiber bewusst aufgeräumt. `materialisieren` legt die Medien als Hardlink in den Bauordner, auf einem anderen Dateisystem als Kopie, und rechnet ihre Prüfsumme vorher nach; fehlt eine Datei oder ist sie beschädigt, bricht es ab, bevor etwas geschrieben ist (Exit 2, Meldung `pruefung.bauen.79` bzw. `.80` als Zeile „ - …“), und `veroeffentlichen.sh` meldet die Reise rot; sie bleibt auf ihrem letzten guten Stand, ohne Stempel und Heartbeat. `pruefen` prüft jede Ablagedatei mit (`file missing in store`, `store checksum mismatch`), `zustand` meldet `ablage_fehlt <n>` (Exit 1 bei n > 0), und `sichern` scheitert, wenn eine verwiesene Datei fehlt. **Sicherung:** Ein Schnappschuss der Datenbank ist ohne die Ablage wertlos. Das Server-Backup der Instanz nimmt `<FR_SPEICHER>/` mit (`reisen.db`-Schnappschuss in `sicherung/` und `ablage/`), in dieser Reihenfolge: erst der Schnappschuss, dann die Ablage (sie wächst nur, eine spätere Ablage enthält alles, worauf der frühere Schnappschuss verweist). **Wiederherstellung:** `sicherung/reisen.db` und `ablage/` zurückholen, als `<FR_SPEICHER>/reisen.db` und `<FR_SPEICHER>/ablage/` einsetzen, `engine/reisespeicher.py pruefen` muss `ok` melden, dann eine Reise mit `vergleichen` gegen ihren erwarteten Ordner prüfen. **Umstellung:** Kein Handschritt. Ein Speicher der Stufe 3 wird beim ersten Öffnen mit der neuen Software auf das neue Schema gehoben; beim Software-Wechsel bringt `engine/neu.py nachziehen-speicher` (im Lauf von `veroeffentlichen.sh`) die vorhandenen Medien in einem eigenen Vorgang `ablage-umstellung` (Person „Software-Nachziehen“) in die Ablage, nach dem Formatvorgang und ebenso höchstens dreimal bei einem Wettlauf mit dem Schreibweg. Die alten Bytes bleiben in der Datenbank liegen (nur anhängen), werden aber nicht mehr gelesen; ein Neuaufbau der Datenbank ohne sie (`ablage-umstellen`) wäre freiwillig und nur zum Verkleinern, er gehört noch nicht zur Software.

**Umzug von `_neu` (#72, 1.11.2026):** Früher lagen Anfragen und Meldungen ohne Reise in `<FR_ABLAGE>/_neu/`. Dieser Ort gilt weiter, solange in `<FR_KONTEN>/neu/` nichts liegt. Umziehen bei angehaltenen Diensten: `mv <FR_ABLAGE>/_neu <FR_KONTEN>/neu && chmod 700 <FR_KONTEN>/neu`.

Der Name der Instanz (`FR_INSTANZ`) steht vor Units, Zonen und nginx-Bausteinen und nennt nur diese Instanz, nicht die Software. Eine zweite Reisegruppe bekommt eine zweite Instanz mit eigenem Namen, eigenem Reisen-Repo und eigenen Ordnern, ihre Daten sind damit von denen der ersten getrennt (#15). Ein gemeinsamer Ort für mehrere Gruppen mit Trennung je Mandant ist #68.

## Datenschutz je Instanz (#15)

Jede Instanz ist für ihre Daten selbst verantwortlich; es wird nichts mit anderen Instanzen geteilt. Die Software legt fest, wer was sieht und wie gelöscht wird. Der Betreiber der Instanz legt die Aufbewahrung der Sicherungen fest.

| Daten | Wer sieht sie | Löschen auf Wunsch einer Person | Aufbewahrung |
|---|---|---|---|
| Konto (Adresse, Name, Sprache, Geräte, Kalender-Abo, Benachrichtigungen) | die Person selbst („Mein Konto“); der Betreiber in der Datenbank | Konto löschen (Mein Konto oder `engine/konten.py loeschen <adresse>`, #381): jede Zeile mit Konto, Adresse oder Namen in allen Tabellen der Kontendatenbank (Mitgliedschaften, Anfragen, Abos, Anmeldungen auch der Claude-App, Einladungen, Wartelisteneintrag, Zählzeilen); die Adresse ist wieder frei. Gesperrt, solange die Person die einzige Organisator:in einer Reise mit weiteren Mitgliedern ist („erst klären“); Reisen nur mit ihr gehen mit Schonfrist mit | bis zum Löschen |
| Eintrag der Warteliste (Adresse, Sprache, Zeiten) | nur der Betreiber (`konten.py warteliste`, Mein Konto) | mit dem Konto derselben Adresse; ohne Konto und Export folgen später | unbestätigt 7 Tage, bestätigt bis zum Löschen |
| Namen in Verlauf und Reise-Stand | alle Mitglieder der Reise | beim Löschen des Kontos wird der Name in jeder Reise, in der die Person Mitglied war, durch „gelöschte Person“ ersetzt: im Verlauf des Reisespeichers, in den bekannten Herkunftsmustern aller Versionen und in der Ablage (`reisespeicher.namen_ersetzen`, Ausnahme vom Nur-Anhängen, ADR-0009); Namen in frei geschriebenen Texten nur dort, wo ein Muster greift. Bei Reisen auf dem alten Weg bleibt der Git-Verlauf | mit der Reise |
| Reise (Pläne, Personen, Entscheidungen) | Mitglieder nach Rolle (`reisend`, `einbringer`, `bestimmer`), nie öffentlich ohne Link | Organisator:innen löschen eine Reise im Reisespeicher auf Mein Konto („Reise löschen …“, zwei Bestätigungen): sofort unsichtbar, nach der Schonfrist (`FR_LOESCHFRIST_TAGE`, Vorgabe 14 Tage) endgültig entfernt, bis dahin „Reise zurückholen“; Reisen auf dem alten Weg nur durch den Betreiber im Reisen-Repo | bis eine Organisator:in sie löscht |
| Meldungen an den Betreiber (Text, Zusammenhang, Reise, Zeitpunkt, Konto; #530) | nur der Betreiber (Mail an alle Betreiber-Konten, `konten.py meldungen`, `my_trips`); die Person selbst im Export | mit dem Konto (Konto löschen entfernt die Zeilen und die Zählzeilen); bereits zugestellte Mails im Postfach des Betreibers löscht dieser selbst | bis erledigt und höchstens bis zum Löschen des Kontos; eine Meldung, die schon zu einem Issue im privaten Reisen-Repo geführt hat, bleibt dort, bis der Betreiber sie auf Wunsch entfernt |
| Rückmeldungen, Aufgaben, Antworten (Ablage) | Organisator:innen der Reise, Absender sehen ihre eigenen | mit der Reise (nach der Schonfrist) | bis zum Löschen der Reise |
| Belege zu Buchungen | hochladende Person und Organisator:innen, bei Freigabe alle der Reise | der Dienst löscht keinen einzelnen Beleg, zurückgezogene bleiben als Datei; mit der Reise wird `<FR_ABLAGE>/<reise>/` ganz entfernt | bis zum Löschen der Reise |
| Sicherungen (Konten-Schnappschuss, Reisespeicher, Archiv der Ablage) | nur der Betreiber | Gelöschtes bleibt bis zur Rotation der Sicherung; nach dem Rückspielen einer alten Sicherung entfernt der tägliche Lauf jede Reise des Löschprotokolls erneut | Ziel höchstens 30 Tage (Aufbewahrung des Server-Backups, Prüfung in `henemm-infra`) |

Diese Tabelle ist die Quelle der Datenschutzerklärung, die der Konnektor unter `/datenschutz` zeigt (#383, Texte in `engine/texte_<sprache>.py`, Entwurf; die rechtliche Prüfung macht der Product Owner). Ändert sich hier etwas, wird die Erklärung im selben PR angepasst; als „folgt“ steht dort nur noch Löschen und Export eines Eintrags auf der Warteliste. Das Löschen von Reise und Konto (#381) nennt sie mit Schonfrist, Sicherungsfrist und der Grenze bei Namen in frei geschriebenen Texten. Daneben liefert der Konnektor `/impressum` (Betreiber aus `FR_BETREIBER_*`, Abschnitt „Einstellungen“) und `/alpha` (Alpha-Hinweis); verlinkt sind alle drei aus der Rechtszeile im Fuß der Reiseseiten und auf Warteliste, Anmeldung, Einladung und Mein Konto. Die nginx-Orte dafür stehen in `nginx-konnektor-orte.inc`; auf einer bestehenden Instanz installiert sie das Hilfsprogramm `nginx-orte-installieren` beim nächsten Veröffentlichen (#445, Abschnitt „nginx-Bausteine abgleichen“; ohne Hilfsprogramm antwortet nginx bis zu `nginx.py anwenden` mit 404).

**Export der Daten (#498):** Auf Mein Konto lädt jede Person mit „Meine Daten herunterladen“ eine ZIP herunter: `person.json` (Name, Adresse, Sprache, Mitgliedschaften mit Rolle, Geräte, Einstellungen für Kalender und Benachrichtigungen; keine Schlüssel, keine Adressen anderer) und je Mitgliedschaft, ohne vorgemerkte und entfernte Reisen, `<reise>/reise/` (die ganze Reise im Dateiformat, mit `reisespeicher.importieren` wieder einlesbar), `<reise>/beitraege/` (Aufgaben, Wünsche, Packstand, Rückmeldungen, wie die Reiseseite sie jedem Mitglied zeigt) und `<reise>/belege/` (die Belege, die die Person sehen darf). Mein Konto läuft im Konnektor, der weder das Reisen-Repo noch sicher den Reisespeicher lesen kann; die Reise holt er darum beim Schreibweg (`GET <KN_SCHREIBDIENST>/<reise>/export` mit `X-Frieda-Dienst`, nur lesend, ohne Sperre: aus dem Speicher über `reisespeicher.exportieren`, sonst `git archive` von `origin/main:reisen/<reise>`, höchstens `ZEIT_EXPORT` = 50 s). Ohne eingerichteten Schreibweg gibt es keinen Export. Der ganze Export hat 55 s (unter der Lesefrist von nginx, 60 s); alles entsteht in temporären Dateien, die danach verschwinden, nichts wird auf dem Server aufbewahrt. Scheitert etwas (außer 404 einer einzelnen Reise, die dann fehlt), bekommt die Person „Export gerade nicht möglich“, nie eine halbe Datei; im Protokoll des Konnektors steht `Error export …`. Je Konto läuft höchstens ein Export zugleich. Kein neues Modul, `deploy.sh` bleibt.

Die KI-Läufe gehören nicht dazu: Frieda enthält keine eigene KI, Reiseinhalte entstehen im AI-Client der Person über den Konnektor (ADR-0001). Es fallen auf dem Server keine Kosten für KI-Läufe an.

## Der Kreislauf

1. **Schreiben:** Was im AI-Client über den Konnektor festgelegt wird (Arten, Merkmale, Werte, Dinge, Optionen, Entscheidungen, Fragen, Wissen, Personen, Status, Einstellungen, neue Reisen), prüft der **Schreibweg** nach den Regeln der Reise und schreibt es sofort nach `main` (siehe „Schreibweg“).
2. **Eingaben:** Rückmeldungen und Antworten von der Webseite und aus der Claude-App, Aufgaben und das Wunsch-Brett liegen live in der Ablage der Reise. Eine Organisator:in arbeitet Rückmeldungen im AI-Client ein (prüfen, mit den Schreibwerkzeugen eintragen, `rueckmeldung_erledigen` mit Kommentar); die Absender sehen „aufgenommen“, „passt nicht“ oder eine Rückfrage.
3. **Veröffentlichen:** `veroeffentlichen.sh` holt `main` in den Bauordner und ruft `deploy.sh` für jede Reise auf. Das geschieht gleich nach jedem Schreibvorgang und sonst alle 5 Minuten. Danach schaltet `freischalten.sh` neue Reisen frei und `zustellen.py` meldet neuen Reisen ihre Links.
4. **Erinnern:** `waechter.sh` läuft täglich, meldet Fristen, fällige Statuswechsel und zu alte Prüfdaten als Meldungen an die Personen; nachschlagen und eintragen tut der AI-Client im Gespräch.

Eine Änderung aus einer Sitzung (Claude Code im Reisen-Repo, nur Software und Betrieb) geht über einen PR nach `main` und von dort denselben Weg ab Schritt 3.

Bis zum 29.10.2026 stand zwischen Eingabe und Veröffentlichen der **Einarbeiten-Lauf** (`einarbeiten.sh`, Pfad-Wächter `<instanz>-einarbeiten.path`, Sammelzeit, ein Lauf von Claude Code je Reise, Aufträge `A-…`). Er ist mit ADR-0001 (Paket O-3) entfallen: Es gibt keinen zweiten KI-Lauf in Frieda, der Eingaben nachträglich deutet.

## Schreibweg

`engine/schreiben.py dienst` (`<instanz>-schreiben.service`, 127.0.0.1:`FR_SB_PORT`) nimmt vom Konnektor Anfragen `POST /<reise>/<werkzeug>` mit dem Dienst-Geheimnis an (`X-Frieda-Dienst`, dasselbe wie beim Rückmeldedienst). Er hält eine eigene Arbeitskopie `<Bauordner>-schreiben` (`FR_SCHREIBKOPIE`), einen Git-Worktree ohne eigenen Branch, den er selbst anlegt und vor jedem Schreibvorgang auf `origin/main` bringt. Ein Vorgang zur Zeit (Sperre `<FR_SPERREN>/<instanz>-schreiben.lock`):

1. Arbeitskopie holen (`origin/main`), eigene Reste verwerfen.
2. Mit dem Code **dieser Arbeitskopie** einen Unterprozess `schreiben.py anwenden` starten, damit Code und Daten denselben Stand haben; der Dienst selbst lädt nur `schreiben.py`, `konten.py`, `reise.py`, `instanz.py` aus `<FR_DIENST>` (`SB_MODULE` in `deploy.sh`).
3. Dort: Person und Rolle gegen `reise.yaml` der Reise prüfen (die Datei gilt vor dem, was der Konnektor sagt), Status (`reise.erlaubt`, Aktion `ontologie`), Form der Angaben; Datei ändern; Probebau (`bauen.Bauer(...).daten()`). Lehnt eine Prüfung ab, wird die Arbeitskopie zurückgesetzt, der AI-Client bekommt den Grund (HTTP 422).
4. Commit mit Reise, Titel, Text, Person, Werkzeug und Datum; `git push origin HEAD:main`. Kam inzwischen etwas anderes an, setzt er darauf auf (Rebase, höchstens dreimal); bei einem Konflikt bricht er ab und meldet „bitte noch einmal“.
5. `betrieb/veroeffentlichen.sh` im Hintergrund, mit `FR_WURZEL` des Bauordners. Hält ein anderer Lauf die Sperre, merkt das Skript das (`<FR_DIENST>/veroeffentlichen-nochmal`), und der laufende Lauf veröffentlicht danach gleich noch einmal (#230).
6. Den neuen Reise-Stand (Nummer, Zeit, Commit) schreibt der Schreibweg nach `<FR_DIENST>/reise-stand/<reise>.gesichert.json`; die Antwort an den Konnektor nennt ihn und den veröffentlichten (Abschnitt „Reise-Stand“).

Die Routendatei (`plan/routen.yaml`; neue IDs über `ids.yaml`, Fragen in `offene-fragen.md`) schreibt er mit ruamel.yaml rund (Kommentare und Form bleiben; `engine/requirements.txt`, bei einer bestehenden Instanz einmal `engine/.venv/bin/pip install -r engine/requirements.txt`). Beim ersten Schreiben zieht er von Hand umbrochene Fließ-Mappings in eine Zeile; `python engine/schreiben.py normalisieren <reise>` tut das vorab in einer Sitzung, damit der erste Commit aus dem Gespräch nur seine Stelle ändert. Hat eine Reise noch keine Routendatei (neu aus der App angelegt), legt der erste Eintrag sie an: Start und Ende aus dem Zeitraum in `reise.yaml`, noch ohne Ort (`start_ende_setzen` ergänzt ihn). Sobald die Reise Arten hat, trägt der Schreibweg den Plan auch in `reise.json` ein (`routen.datei`), damit der Generator ihn liest, dazu die Abschnitte für Tagesplan und Unterkünfte (`routen.tagesplan`, `routen.unterkuenfte`, neue `W-…`), damit die Seite die Tage zeigt.

Auch der Rückmeldedienst schickt ihm Anfragen: Stellt eine Organisator:in den Status der Reise auf der Reiseseite um (#513), reicht er die Wahl als `reise_status_setzen` weiter. Er findet den Schreibweg über `RM_SCHREIBDIENST`, sonst `KN_SCHREIBDIENST`, sonst `http://127.0.0.1:<FR_SB_PORT>` (Vorgabe 8773); eine Einheit muss dafür nichts Neues setzen.

Der Dienst läuft als Dienstbenutzer mit dessen `git`-Anmeldung (`gh` als Credential-Helfer, `PATH` aus `FR_PFAD`), ohne `ProtectHome`, weil die Arbeitskopie neben dem Repo liegt. `GET /gesund` antwortet `{"gesund": true}`, wenn das Repo erreichbar ist. Von Hand: `frieda/betrieb/…`: `FR_WURZEL=<Bauordner> engine/.venv/bin/python engine/schreiben.py vorbereiten` legt die Arbeitskopie an. Protokoll: `journalctl -u <instanz>-schreiben`. Eine Instanz ohne diesen Dienst setzt `KN_SCHREIBDIENST` nicht; der Konnektor bietet die Schreibwerkzeuge dann nicht an, und neue Reisen lassen sich aus der Claude-App nicht anlegen.

### Speicherweg (Stufe 2, #347, ADR-0009)

Welcher Weg schreibt, entscheidet die Instanz je Reise mit `FR_SPEICHERREISEN` in `betrieb/einstellungen.env` (kommagetrennte Reisenamen, Vorgabe leer). Eine Reise in der Liste schreibt über den Reisespeicher (`engine/reisespeicher.py`), jede andere bis Stufe 5 wie oben über Git (`engine/schreiben_git.py`, `engine/stand_git.py`); der Git-Weg lehnt eine Reise der Liste ab (503, kein Doppelschreiben). Steht eine Reise in der Liste, hat aber noch keinen Eintrag im Speicher, antwortet der Schreibweg 503 ohne jede Wirkung; ist die Datenbank nicht erreichbar, ebenfalls 503 („Speicher nicht erreichbar“).

Ablauf des Speicherwegs: Sperre der Reise wie oben (bei `reise_anlegen` die Sperre „reisen“), Stand-Nummer merken und den Stand in einen temporären Ordner exportieren, dann `schreiben.py anwenden` mit dem Code aus `<FR_DIENST>` (deshalb enthält `SB_MODULE` alle Module von Werkzeugen und Probebau, dazu Vorlage, `vendor/` und `reisevorlage/`). Rolle, Werkzeug und Probebau wie oben; der Unterprozess trägt das Ergebnis als genau einen Vorgang ein (Person, Rolle, Werkzeug, Titel, Grund, Kennung; eine Transaktion, `erwartet` = gemerkter Stand). Hat jemand dazwischen geschrieben, antwortet er 503 „bitte noch einmal“, ohne etwas zu überschreiben. Die Antwort nennt in `commit` die Vorgangs-Nummer. Der temporäre Ordner wird in jedem Fall gelöscht; kein git, kein Push. `GET /gesund` fragt die Datenbank (bei Git-Reisen daneben auch das Repo), `GET /<reise>/buchung/<B-id>` liest `plan/routen.yaml` aus dem Speicher.

Veröffentlichen und Nachziehen aus dem Speicher (Stufe 3, #348): `betrieb/veroeffentlichen.sh` baut eine Reise der Liste aus dem Speicher (Abschnitt „Veröffentlichen“, Reisen aus dem Reisespeicher), ohne GitHub, und stellt sie nach einem Software-Wechsel selbst um; `publish_status` zeigt ihren echten Stand. Ihre Git-Kopie bleibt bis Stufe 5 liegen und wird weder gebaut noch vom Workflow „Software nachziehen“ umgestellt. Vorbedingungen und Schritte vor dem ersten Umschalten einer echten Reise stehen im Abschnitt „Umschaltung einer Reise“ unten; ohne Stempel „gleich“ des Vergleichslaufs verweigern Veröffentlichen und Schreibweg eine Reise, die noch in Git liegt (Stufe 5, #350). Die Datenbank (Modus 600) müssen Dienstbenutzer des Schreibwegs, des Veröffentlichens und des Wächters öffnen können; falsche Rechte zeigen sich als 503 „Speicher nicht erreichbar“ bzw. als Exit 2 von `materialisieren`. Messen: `betrieb/messlauf-schreibweg.py --weg speicher|git` (Kennzahlen nacheinander und parallel).

**Anfangsvorgang und Vergleichslauf:** Eine Git-Reise kommt mit genau einem Vorgang in den Speicher: `engine/reisespeicher.py importieren reisen/<reise> <reise> <wer> --grund "vorher in Git" --ab <n−1>`, wobei `n` ihre bisherige Stand-Nummer aus Git ist (`importieren` setzt den Stand auf `ab + 1`, die Nummer läuft also ohne Sprung weiter). `FR_WURZEL=<Bauordner> betrieb/vergleichslauf.sh [--bis N] [<reise>…]` hält danach den Dateistand aus Git (`git archive HEAD`, der Bauordner bleibt unberührt) samt den von Git ignorierten Dateien der Reise im Bauordner (`git ls-files --others --ignored --exclude-standard`, etwa die Offline-Grundkarten unter `medien/karte/`, die `importieren` mit übernimmt, #479; ungesicherte, nicht ignorierte Dateien zählen nicht) gegen den Export aus dem Speicher (`engine/reisespeicher.py vergleichen <reise> <ordner> [--bis N]`, nur Prüfsummen): Ausgabe je Unterschied `nur im Speicher: …`, `nur im Ordner: …`, `verschieden: …`, am Ende `gleich` oder `<n> Unterschiede`; Exit 0 gleich, 1 Unterschied, 2 Fehler (insgesamt das schlimmste Ergebnis). Ohne Reise vergleicht er jede, die in Git liegt und einen Eintrag im Speicher hat. Je Reise schreibt er den Stempel `<FR_DIENST>/vergleich/<reise>.json` (`zeit`, `ergebnis` gleich | unterschied | fehler, `stand`, `git`, `unterschiede`, `baum` = `git rev-parse HEAD:reisen/<reise>`, `arbeitsordner` = Anzahl der ignorierten Dateien, nur Auskunft; eine spätere Änderung an ihnen macht den Stempel nicht ungültig). Er läuft von Hand, ohne Timer. Seit Stufe 5 (#350) ist der Stempel „gleich“ die Freigabe der ersten Umschaltung (Abschnitt „Umschaltung einer Reise“).

### Umschaltung einer Reise

Mit Stufe 5 (#350, ADR-0009) kommen die Reisen einer Instanz eine nach der anderen aus Git in den Reisespeicher. Die Software bleibt dabei im Reisen-Repo (Submodul, Workflow „Software nachziehen“); nur die Reisedaten brauchen GitHub danach nicht mehr.

1. **Vorbedingungen:** Das Server-Backup der Instanz sichert `<FR_SPEICHER>/sicherung/` außer Haus, und ein Rückspielversuch ist gelungen (#347, Arbeit an der Instanz). Die Umschaltung ist vorher im Issue angesagt. Der Bauordner ist aktuell: Ein Lauf von `veroeffentlichen.sh` ist grün durchgelaufen, und niemand schreibt mehr über den Git-Weg in diese Reise (der Vergleich nutzt den lokalen `HEAD`, ohne Netz).
2. **Reihenfolge:** erst die Testreise, dann die kleinste echte Reise, dann die übrigen, je eine nach der anderen; jede erst nach dem Abschluss der Prüfung der vorigen, nie zwei gleichzeitig.
3. **Schritte je Reise:** (1) Anfangsvorgang `engine/reisespeicher.py importieren reisen/<reise> <reise> <wer> --grund "vorher in Git" --ab <n−1>`; (2) `FR_WURZEL=<Bauordner> betrieb/vergleichslauf.sh <reise>` muss `gleich` melden: Der Stempel ist die Freigabe, ohne ihn oder mit veraltetem Stempel weigern sich Veröffentlichen und Schreibweg (Sperre, unten); (3) Schalter: die Reise in `FR_SPEICHERREISEN` von `betrieb/einstellungen.env` des Reisen-Repos aufnehmen und committen; (4) der nächste Lauf von `veroeffentlichen.sh` baut sie aus dem Speicher und legt den Stempel `<FR_DIENST>/reise-stand/<reise>.gebaut` an; (5) Prüfung im Konnektor: `publish_status` meldet „enthalten: ja“ für den Reise-Stand, eine Probe-Änderung an einer Testreise (nie an einer echten Reise zum Probieren) wird veröffentlicht, die Seite lädt, auch offline; (6) Abnahme an beiden Reisetypen, nie nur an der Wanderung; (7) die Git-Kopie liegen lassen.
4. **Die Sperre:** Gesperrt ist eine Reise genau dann, wenn sie in `FR_SPEICHERREISEN` steht, in Git liegt (`reisen/<reise>` im Commit `HEAD` des Bauordners), keinen Stempel `.gebaut` hat und keinen gültigen Stempel „gleich“. Gültig ist der Stempel, solange der Git-Baum der Reise derselbe ist wie beim Vergleich (`baum`) und der Speicher nicht hinter `stand` zurückgefallen ist; Commits außerhalb von `reisen/<reise>` und spätere Vorgänge des Schreibwegs machen ihn nicht ungültig, ein Stempel ohne `baum` (von vor Stufe 5) gilt als veraltet. Lösen: `betrieb/vergleichslauf.sh <reise>` erneut laufen lassen. Die Sperre trifft nur Reisen ohne `.gebaut`: Reisen, die nur im Speicher liegen (neu aus der Claude-App angelegt), und Reisen mit Stempel `.gebaut` (schon umgeschaltet, etwa die Testreise) sind frei; für eine schon umgeschaltete Reise mit `.gebaut` ist nach dem Software-Wechsel kein Handschritt nötig. Gesperrt überspringt das Veröffentlichen die Reise mit dem Hinweis „not cleared for the switch (<grund>)“ im Protokoll, ohne Rot und ohne Meldung, die Seite bleibt auf ihrem Stand; der Schreibweg antwortet 503 („noch nicht freigegeben“) und schreibt nichts. Prüfen von Hand: `engine/reisespeicher.py umschaltung <reise>` (Ausgabe `frei` oder `gesperrt <grund>`, ändert nichts). Die Sperre hat keinen Schalter zum Abschalten.
5. **Rückweg Speicher nach Git** (Rückfallplan während der Umschaltung): (a) Beteiligte informieren, dass bis zum Abschluss nicht geschrieben wird; (b) `engine/reisespeicher.py exportieren <reise> <leerer Ordner>` (neuester Stand, byte-gleich); (c) den Ordner als `reisen/<reise>` ins Reisen-Repo übernehmen und die Reise aus `FR_SPEICHERREISEN` nehmen, beides im selben Commit, vorspulen auf `main`; (d) `<FR_DIENST>/reise-stand/<reise>.gebaut` und `<FR_DIENST>/reise-stand/<reise>.lauf.json` entfernen, damit bei einer späteren zweiten Umschaltung die Sperre wieder gilt; (e) der nächste Lauf baut die Reise aus Git; zur Kontrolle meldet `vergleichslauf.sh <reise>` `gleich` für den Stand, aus dem exportiert wurde. Die Reise bleibt im Speicher (nur anhängen), er wird nicht gelöscht.
6. **Zurücksetzen auf einen früheren Stand:** `engine/reisespeicher.py verlauf <reise>` zeigt die Vorgänge; `engine/reisespeicher.py zuruecksetzen <reise> <bis> <wer> <grund>` schreibt einen neuen Vorgang mit dem Inhalt des Stands `<bis>`, der Verlauf bleibt; der nächste Lauf veröffentlicht ihn.
7. **Das alte Repo als Archiv:** Nach der Umschaltung aller Reisen schreibt niemand mehr in `reisen/<reise>` des Reisen-Repos; der Stand dort ist das Archiv bis zum Umschalten. Mit #454 holt die Instanz die Software direkt (Abschnitt „Umzug auf den Software-Klon“); das Reisen-Repo bleibt bis zum Folge-Issue (Rückbau des Git-Wegs) unangetastet liegen, es wird nicht gelöscht.

**Alle Reisen im Speicher (#454, Lieferung 1):** Im Speicher ist, was im Speicher steht: Eine Reise gilt als Speicherreise, sobald sie dort mindestens einen Vorgang hat und ihre Umschaltung nicht offen ist (`engine/reisespeicher.py speicherreisen`, `instanz.speicherreisen()`; Sperre wie in Punkt 4). `FR_SPEICHERREISEN` ist nur noch Übergang: gelesen, wirkungslos, keine Fehlermeldung, kein Handschritt. Ist der Speicher nicht lesbar, brechen Schreibweg und Veröffentlichen ab (fail closed, #361), nie mit „keine Reisen“. Eine neue Reise (`trip_create`, `reise_anlegen`) entsteht immer im Speicher. Übrige Reisen aus `reisen/` des Bauordners schaltet `veroeffentlichen.sh` selbst um, sobald eine Datenbank des Speichers da ist (`engine/reisespeicher.py umschalten <reise>`): Anfangsvorgang aus dem Git-Stand (`HEAD`, dazu ignorierte Dateien wie beim Vergleichslauf), Vergleich byte-gleich, Stempel `gleich`; danach baut sie der Speicher-Teil. Ist sie nicht gleich, bleibt sie in Git, mit der Warnzeile „stays in git“ im Protokoll und ohne Meldung; weder Git noch der Speicher verlieren dabei etwas, nichts wird überschrieben. Bricht die Umschaltung zwischen Anfangsvorgang und Stempel ab, vergleicht der nächste Lauf gegen den vorhandenen Anfangsvorgang (kein zweiter). **Git hat sich seit dem Anfangsvorgang geändert** (die Umschaltung war offen, geschrieben wurde über den Git-Weg): Stehen für die Reise im Speicher nur Importe, ist Git die Wahrheit; der Lauf hängt den aktuellen Git-Stand als weiteren Import an (nur anhängen, ADR-0009), vergleicht erneut und stempelt bei `gleich`. Hat dort jemand anderes geschrieben (ein anderer Vorgang als ein Import), bleibt die Reise in Git, mit der Warnzeile „stays in git“ und ohne Alarm; welcher Stand gilt, entscheidet dann ein Mensch (`betrieb/vergleichslauf.sh <reise>` zeigt die Unterschiede). Ob es die Datenbank gibt, entscheidet in der Shell `engine/reisespeicher.py datenbank`; ein nicht durchsuchbarer Speicherordner macht den Lauf rot, nie „keine Reisen“ (#361). Die Schritte (1) bis (3) oben sind damit für neue Umschaltungen nicht mehr nötig.
8. **GitHub-Ausfall:** Scheitert `git fetch` bei einer Instanz mit `FR_SPEICHERREISEN`, ist das kein Fehler des Laufs: Die Reisen aus dem Speicher sind schon veröffentlicht, nur die Software-Aktualisierung und die Reisen, die noch in Git liegen, warten (Warnung „git fetch failed“ im Protokoll). Exit 1 gibt es dann nur für rote Reisen aus dem Speicher; Stempel `veroeffentlichen-erfolg` und Heartbeat nur, wenn keine Reise mehr in Git liegt, sonst endet der Lauf mit 0 ohne Heartbeat. Der Merker `<FR_DIENST>/software-wartet` (`seit=`, `gemeldet=`) hält die Störung fest; nach `FR_SOFTWARE_WARTET_STUNDEN` Stunden (Vorgabe 6) steht genau eine Warnzeile „Software update waiting“ im Protokoll und `gemeldet=1` im Merker, den der Monitor der Instanz als Warnung liest; eine Nachricht an den Betrieb geht nicht. Gelingt `git fetch` wieder, wird der Merker gelöscht.

**Fehlerfälle:** Lehnt der Schreibweg ab (Rolle, Status, Form, Probebau), bleibt alles unverändert, und der AI-Client bekommt den Grund im Gespräch. Scheitert `git push` (Konflikt nach drei Versuchen, kein Netz), meldet er „bitte noch einmal“; nichts ist halb geschrieben. Bleibt der Dienst stehen (`failed`), sieht das der Monitor der Instanz (siehe „Überwachung“), der Konnektor meldet der Person „Schreibweg nicht erreichbar“.

## Belege

Belege zu Buchungen (Buchungsbestätigung, Ticket; `engine/belege.py`, #76, 29.10.2026) liegen in `<FR_ABLAGE>/<reise>/belege/` mit dem Verzeichnis `belege.json` daneben, nie im Repo und nie in den Web-Ordnern. Der Rückmeldedienst ist ihr einziger Schreiber (`POST /<reise>/belege/<B-id>`, nur angemeldet oder über den Dienst-Header, nie mit bloß eingetipptem Namen; die Buchung muss veröffentlicht sein, oder der Konnektor hat sie beim Schreibweg im Repo geprüft und schickt `X-Frieda-Buchung: im-repo` mit, damit der Beleg sofort nach dem Anlegen geht; Body ist die Datei, höchstens 10 MB, Typ am Inhalt geprüft: PDF, JPEG, PNG, WebP, HEIC, dazu Text als `.txt`/`.md` für die Abschrift einer Bestätigung aus dem Gespräch, Konnektor `beleg_anlegen`, Issue #135; 100 MB und 200 Dateien je Reise) und liefert sie aus (`GET /<reise>/belege/<D-id>`), nur an die hochladende Person und Organisator:innen, oder an alle, wenn eine Organisator:in den Beleg freigegeben hat. Nichts wird gelöscht; zurückgezogene Belege bleiben als Datei. Der nginx-Baustein der Reise hat dafür einen eigenen `location`-Block (`api/belege/`, `client_max_body_size 11m`); `freischalten.sh` erneuert den Baustein jeder Reise, wenn sich die Vorlage ändert (gleicher Pfad, nginx geprüft; der Pfad wird aus dem Baustein gelesen und muss nicht mit dem Ordner der Reise beginnen, etwa bei einem von Hand angelegten Baustein). Die Prüfungen vor dem Veröffentlichen laufen in einem eigenen Testordner (`--basetemp`), damit gleichzeitige pytest-Läufe auf demselben Rechner sie nicht stören. Belege gehören zur Sicherung der Ablage wie Rückmeldungen und Aufgaben.

## Kalender

Kalender (`engine/kalender.py`, #77) gibt es zweimal. **Je Reise als Datei:** Der Rückmeldedienst liefert `GET /<reise>/kalender.ics` (ganze Reise, `?id=<ID>` für ein Ding) aus den veröffentlichten Daten und den Aufgaben der Ablage, wie die Seite ohne Anmeldung, nur unter dem geheimen Link. **Je Person über alle Reisen:** Der Konnektor liefert das Abo unter `<FR_KN_ADRESSE>/kalender/<wort>.ics` (Kalender-Apps melden sich nicht an; das Wort ist je Konto aus dem Dienst-Geheimnis berechnet, nicht gespeichert) und den Download auf „Mein Konto“ (`/konto?kalender=datei`, angemeldet). Was darin steht, stellt jede Person auf „Mein Konto“ ein (Einträge, nur eigene Aufgaben, Erinnerungen, Reisen); die Einstellungen und ein Zähler für „neuer Link“ liegen in `konten.db`, Tabelle `kalender_abo`. Es zählen nur Reisen, in denen das Konto Mitglied ist; ein gesperrtes Konto hat kein Abo. nginx: Baustein `api/` der Reise und `/kalender/` im Baustein des Konnektors; der Konnektor braucht `KN_BASIS` (steht in der Vorlage `konnektor.service`). Nur Standardbibliothek, weil die Dienste mit dem Python des Systems laufen. Wird das Dienst-Geheimnis ersetzt, gelten alle Abo-Links nicht mehr.

Das Abo folgt dem, was Kalender-Programme erwarten (1.11.2026, nach dem Fehler im Apple Kalender): Die Adresse ist HTTPS mit gültigem Zertifikat; Apple-Geräte holen `webcal://` über HTTPS und fragen nur, wenn das scheitert, ob es „ohne SSL“ gehen soll. Vor dem Laden prüfen Apps die Adresse mit `HEAD`, `OPTIONS` oder `PROPFIND` (ist das CalDAV?); der Konnektor antwortet darauf mit 200, 204 (`Allow: GET, HEAD, OPTIONS`) und 405, nie mit 501, das ein Abo scheitern lässt. Jede Antwort trägt ein `ETag` (ohne `DTSTAMP` berechnet) und `Cache-Control: private, no-cache`; fragt die App mit `If-None-Match`, kommt bei gleichem Inhalt 304. Der Kalender trägt `NAME`, `X-WR-CALNAME`, `REFRESH-INTERVAL` und `X-PUBLISHED-TTL` (6 Stunden) und bleibt auch leer gültig (eine Zeitzone UTC statt keines Bestandteils, RFC 5545). Das Abo spricht die Sprache des Kontos. „Mein Konto“ und der Konnektor geben je Programm den passenden Weg: `webcal://` (iPhone, iPad, Mac, Outlook für Windows), Google Kalender („Kalender hinzufügen“ über `calendar.google.com/calendar/render?cid=`), Outlook im Web (`outlook.live.com/calendar/0/addfromweb`) und die https-Adresse zum Kopieren. Google und Outlook im Web holen das Abo von ihren eigenen Servern; die Adresse muss deshalb aus dem Internet erreichbar sein und darf nicht nach Herkunft oder User-Agent sperren. Der server-Block der Instanz (nicht Teil der Bausteine) soll `http://` mit 301 auf `https://` umleiten, damit auch der Weg „ohne SSL“ ankommt. Jede Antwort des Konnektors trägt den Kopf `X-Frieda: konnektor`; `deploy.sh` fragt nach jedem Deploy `/gesund`, `/anmelden`, `/kalender/…`, `/schrift/…` und `/favicon.svg` über `FR_KN_ADRESSE` ab und warnt im Protokoll (keine Meldung über `FR_MELDEN`, #445: ein fehlender Ort ist kein Ausfall), wenn ein Weg bei nginx statt beim Konnektor endet; die Abweichung der nginx-Bausteine meldet `nginx_abgleichen` einmal als Issue, überwacht wird sie als Warnung im Teil-Check von `monitor.sh` der Infrastruktur (so blieb das Abo der ersten Instanz unbemerkt hinter einer 404-Seite von nginx). Beim Veröffentlichen geschieht das einmal je Lauf nach dem Freischalten aller Reisen (`wege_pruefen` in `gemeinsam.sh`, `FR_WEGE_SPAETER`), nicht je Reise: Die Abrufe kommen vom Server selbst und zählen in nginx in dieselbe Begrenzung wie die Prüfung von `freischalten.sh`, je Reise abgefragt bekamen die letzten Reisen 429. Prüfen von außen: `curl -I <abo-adresse>` (200, `text/calendar`), `curl -X OPTIONS -i <abo-adresse>` (204), `curl -X PROPFIND -i <abo-adresse>` (405).

## Zeitgrenzen und Sperren des Schreibwegs

Ein Schreibvorgang darf samt Wartezeit auf die Sperre nicht länger dauern, als nginx auf den Konnektor wartet (`proxy_read_timeout`: 300 s für `/mcp` in `nginx-konnektor-orte.inc`, sonst die Vorgabe von nginx mit 60 s, Begründung in `nginx-konnektor.inc`; bis 1.11.2026 30 s), sonst erreicht die Meldung die Claude-App nie (#118, #163). Darum gilt (`engine/schreiben.py`; ein Test prüft die Summe gegen jede Lesefrist der nginx-Vorlage): `ZEIT_GESAMT = 25` Sekunden für Sperre, Vorbereiten der Arbeitskopie (jeder `git`-Aufruf mit dem Rest der Frist) und Anwenden zusammen, davon höchstens `ZEIT_SPERRE = 3` Wartezeit auf die Sperre, und danach `ZEIT_PRUEFUNG = 3` Sekunden Reserve für die Ergebnisprüfung. Eine Antwort kommt also nach höchstens 28 Sekunden. Ausnahme `kartenpunkte_holen` (#240): Davor liegt, ohne Sperre, ein Vorab-Fenster von höchstens 55 Sekunden (`ZEIT_VORAB`: Lesekopie, Rollenprüfung, Abruf bei Overpass, `docs/werkzeuge.md`), danach beginnt `ZEIT_GESAMT` neu; die Antwort kommt nach höchstens 83 Sekunden, unter den 120 Sekunden, die der Konnektor auf den Schreibweg wartet. Wer die nginx-Grenze ändert, prüft die Werte mit.

Das Anwenden läuft als Unterprozess in eigener Prozessgruppe; bei Fristablauf wird die ganze Gruppe beendet, auch ein laufendes `git push`. Jeder Vorgang bekommt eine kurze Kennung, die als Zeile `Frieda-Vorgang: <Kennung>` in der Commit-Nachricht steht. Nach einem Abbruch im Anwenden holt der Schreibweg `origin/main` und sucht die Kennung (beides zusammen höchstens `ZEIT_PRUEFUNG`). Die Meldungen:

| Fall | Code | Meldung | Protokoll |
|------|------|---------|-----------|
| eingetragen trotz Abbruch | 200 | „Es hat länger gedauert, ist aber eingetragen.“ | `Timeout <werkzeug> 504: aborted, saved` |
| nicht eingetragen (Abbruch im Vorbereiten oder Kennung nicht gefunden) | 504 | „… ist nicht eingetragen; bitte noch einmal versuchen.“ | `Timeout <werkzeug> 504: aborted, not saved` |
| Prüfung nicht möglich (`origin` nicht erreichbar) | 504 | „… bitte prüfen, ob es angekommen ist.“ | `Timeout <werkzeug> 504: aborted, unchecked` |
| Sperre belegt | 429 | „… bitte gleich noch einmal versuchen.“ | `Locked <werkzeug> 429: …` |
| abgelehnt | 422 | Grund der Regel | `Rejected <werkzeug> 422: <Grund>` (#121) |
| unerwarteter Fehler im Dienst | 500 | „Schreiben fehlgeschlagen (Fehler im Dienst) …“ | `Error <werkzeug> 500: <Art>: <Text>` |

Auf dem Speicherweg ist die Nachprüfung lokal im Speicher: Der Schreibweg sucht die Kennung in der Datenbank (nur lesen, höchstens `ZEIT_PRUEFUNG`), ohne fetch; ein getöteter Unterprozess hat seine Transaktion zurückgerollt, „nicht eingetragen“ ist dort also sicher. Läuft die Frist schon beim Export ab, ist nichts angewendet (504 „nicht eingetragen“). Die Fristen und die Tabelle gelten für beide Wege; „Prüfung nicht möglich“ heißt dort: Datenbank nicht lesbar.

Ein Restrisiko bleibt beim Git-Weg: Wird ein `git push` im Moment der Übertragung beendet, kann der Eintrag noch ankommen, nachdem „nicht eingetragen“ gemeldet wurde; eine Wiederholung kann ihn dann doppelt eintragen.

Ein beendetes `git` kann Sperrdateien (`index.lock` u. ä.) hinterlassen. Vor dem Vorbereiten entfernt der Schreibweg darum veraltete `*.lock` im eigenen git-Ordner der Arbeitskopie (`<Repo>/.git/worktrees/<Name>/`); das ist sicher, weil er dabei die Sperre der Reise hält. Sperren im gemeinsamen git-Ordner des Repos fasst er nicht an, dort arbeiten andere Reisen und das Veröffentlichen.

Sperre und Arbeitskopie (`<wurzel>-schreiben-<reise>`) gibt es je Reise (#119): Was bei einer Reise hängt, hält die anderen nicht auf. Betriebsprotokolle (stderr, Journal) sind englisch, unabhängig von der Sprache der Personen (ADR-0006). Das Protokoll des Schreibwegs (`journalctl -u <instanz>-schreiben`) nennt Ablehnungen mit Werkzeug und Grund (einzeilig, höchstens 200 Zeichen) und für jeden Vorgang mit jedem Code eine Zeile `Done <werkzeug> <code> in <Sekunden> s`. An diesen Dauern lässt sich prüfen, ob `ZEIT_GESAMT` für große Reisen reicht.

## Sprachen

Die Texte der Software stehen in `engine/texte_<kürzel>.py`. `deploy.sh` nimmt jede Sprachdatei im Ordner `engine/` von selbst in die Modullisten von Rückmeldedienst, Konnektor und Schreibweg auf (`SPRACHDATEIEN`); eine neue Sprache braucht dort keinen Eintrag ([sprachen.md](sprachen.md)). Die Sprache einer Person steht in der Spalte `konten.sprache` der Kontendatenbank; auf einer vorhandenen Datenbank fügt der erste Start des neuen Stands die Spalte selbst hinzu (`ALTER TABLE`), von Hand ist nichts zu migrieren. Die Sprache einer Reise steht in ihrer `reise.yaml`; fehlt das Feld, bricht der Bau (`pruefung.reise.sprache_fehlt`), `neu.py nachziehen` trägt `de` ein. Meldungen des Wächters (`meldungen.jsonl`) und der Kalender folgen der Sprache der Reise.

## Veröffentlichen

**Software direkt (#454):** Im Software-Klon (`FR_WURZEL=<FR_SEITEN>/_software`) baut ein Lauf zuerst die Reisen aus dem Speicher mit der Software, die da ist. Dann `git fetch origin main` (öffentlich, ohne Anmeldung, ohne Reisen-Repo, ohne `gh`). Ein neuer Commit wird **geprüft, bevor der Klon umschaltet**: Nachweis der Pflichtprüfungen genau dieses Commits auf GitHub (`tests (leer)`, `tests (instanz)`, `gitleaks`; Abfrage ohne Anmeldung, einmal je Stand), sonst die Tests auf dem Server in einem eigenen Arbeitsbaum des Commits (`git worktree`), der Klon bleibt dabei unverändert. Rot: Rot-Datei am Software-Commit, Alarm wie unten, der Klon bleibt auf seinem Stand. Ändert der Commit `engine/requirements.txt`, entsteht vor der Prüfung eine eigene Umgebung neben der laufenden (`<FR_DIENST>/python.neu`), die Tests auf dem Server laufen mit ihr; rot verwirft sie, die laufende bleibt unverändert. Grün: Klon vorspulen und die neue Umgebung in einem Schritt an die Stelle von `<FR_DIENST>/python` setzen (die vorige bleibt als `python.alt`; die Umgebung wird dabei verschoben, aufgerufen wird sie deshalb immer als `bin/python -m …`); ändert sich dabei `veroeffentlichen.sh`, startet es sich mit `exec` neu. Dann bringt `deploy.sh --dienste` den Code der Dienste auf den neuen Stand. **Rückfall** nur, wenn dieser Deploy scheitert: Der Lauf setzt den Klon auf `<FR_DIENST>/software-gut` zurück, setzt die vorige Python-Umgebung wieder ein, bringt die Dienste mit `deploy.sh --dienste` auf diesen Stand und schreibt die Rot-Datei am neuen Commit (er wird nicht im nächsten Takt erneut ausgerollt, erst nach der Frist der Rot-Datei oder mit einem neuen Commit; ein Alarm je Rot-Phase). Erst nach grünem Deploy der Dienste zieht der Speicher-Teil jede Reise auf den neuen Stand nach (`neu.py nachziehen-speicher`); so läuft nach einem Rückfall nie alter Code auf schon umgestellten Reisedaten. Scheitert danach etwas anderes (Speicher kurz nicht lesbar, Umschaltprüfung, Deploy einer Reise), gibt es keinen Rückfall: Der Lauf ist rot, die Seiten bleiben auf ihrem letzten guten Stand, der nächste Lauf versucht es wieder. Nur ein ganz grüner Lauf schreibt `veroeffentlicht` und `software-gut` (beide der Commit der Software, ebenso die Kennung in `.gebaut`), gleicht Units und nginx ab und ruft den Heartbeat. Danach laufen die Prüfungen der Instanz aus `<FR_DIENST>/instanz/tests`, wenn es sie gibt; rot ist eine Warnung, sie sperren nie. Ein Wechsel in einem halben Zustand (Abbruch zwischen den Schritten) wird beim nächsten Lauf fortgesetzt: Klon-Commit, `software-gut`, `veroeffentlicht` und Rot-Datei werden bei jedem Start neu gelesen.

**Alte Anordnung (bis zum Umzug):** `betrieb/veroeffentlichen.sh` holt `origin/main`, spult den Bauordner vor und bringt das Submodul auf den festgehaltenen Stand. Hat das Vorspulen die Einstellungsdatei geändert (Prüfsumme davor und danach; Erscheinen oder Verschwinden zählt mit), schreibt es „Settings changed by the update, restarting.“ ins Protokoll und startet sich mit denselben Argumenten neu, höchstens einmal je Lauf, damit Bau und Freischalten schon die neuen Werte nutzen (#242). Die Prüfungen laufen überall in derselben Umgebung (#202): `engine/requirements.txt` hält jede Bibliothek mit Version und Hash fest (erzeugt mit pip-tools aus `engine/requirements.in`, Befehl steht dort), `engine/tests/playwright/package-lock.json` die Playwright-Version. CI installiert genau diese Stände und prüft zusätzlich mit nachgestellten Einstellungen einer Instanz. `veroeffentlichen.sh` installiert sie vor den Prüfungen nach, wenn sich eine der Listen geändert hat: die Bibliotheken in `FR_PYTHON` (Prüfsumme in `<FR_DIENST>/requirements.sha256`; danach starten Schreibweg und Push-Dienst beim ersten Deploy des Laufs neu), Playwright mit `npm ci` in eine eigene Kopie `<FR_DIENST>/playwright` (Browser ohne `--with-deps`, die Systembibliotheken gehören zur Einrichtung), die die Prüfungen über `PLAYWRIGHT_MODUL` bekommen. Scheitert eine Installation, endet der Lauf ohne Prüfung und Bau, und der nächste versucht es wieder. Eine neue Bibliothek oder Version kommt also nur über einen Commit, den CI in derselben Umgebung geprüft hat. Danach laufen die Tests einmal. Dann ruft es `deploy.sh` für jede Reise mit `reise.json` auf und gibt ihm den geprüften Stand mit (`FR_GEPRUEFT`), damit die Tests nicht je Reise erneut laufen. Der Lauf hat niedrige Priorität (`Nice=10`, `IOSchedulingPriority=7` im Dienst `veroeffentlichen.service`; der Schreibweg startet ihn mit `nice` und `ionice`), damit Schreibvorgänge während der Tests nicht warten (#120); fehlen `nice` oder `ionice`, startet er ohne sie. Die Ausgabe dieses angestoßenen Laufs geht nach `/dev/null`: Sonst hielte das Skript die Leitung zum Schreibweg bis zu seinem Ende offen, und jeder Schreibvorgang wartete darauf. Verloren geht dabei nichts Wesentliches: Ein Erfolg zeigt sich an `<FR_DIENST>/veroeffentlichen-erfolg` und am Heartbeat, ein Infrastrukturfehler wird vom Timer wiederholt, ein roter Stand wird übersprungen und meldet sich nach der Schwelle selbst (unten); die Ausgabe des Timers steht im Protokoll (`journalctl -u <instanz>-veroeffentlichen`). Gemerkt wird der Stand in `<FR_DIENST>/veroeffentlicht`. Nur ein ganz gelungener Lauf merkt ihn. Ist der Ordner nicht auf `main` oder nicht sauber, überspringt es den Lauf. `--immer` veröffentlicht auch ohne neuen Stand und prüft auch einen bekannten roten Stand neu.

**Was sperrt (#142):** Eine Inhaltsfrage einer Reise hält das Veröffentlichen nie an. Sperren können nur zwei Dinge:

- **Tests der Software rot** (`pytest engine/tests`): Keine Reise wird angefasst, Exit 1.
- **Bau oder Startprobe einer Reise gescheitert** (Baufehler, `deploy.sh` endet mit Exit 2): Nur diese Reise bleibt auf ihrem letzten guten Stand, die anderen werden gebaut und freigeschaltet. Die **Startprobe** (`betrieb/startprobe.mjs`, #395, Lehre aus #387) lädt die gebaute Seite im Browser; ein Seitenfehler beim Start, `console.error`, eine leere Seite oder die sichtbare Startfehler-Meldung (`#startfehler`, „Startfehler-Meldung sichtbar“, #387) machen sie rot. Ohne `PLAYWRIGHT_MODUL` nimmt `deploy.sh` die Kopie der Instanz in `<FR_DIENST>/playwright` (sonst fiele die Probe bei Reisen aus dem Reisespeicher aus, die vor dem Einrichten der Abhängigkeiten gebaut werden); ohne Playwright gibt es nur eine Warnung. Für die Überwachung prüft `startprobe.mjs <modul> --adressen` die ausgelieferten Seiten: Zeilen „<name><TAB><adresse>“ über stdin, je Seite eine Zeile „<name>: gut“ oder mit dem Fehler; die geheimen Links stehen nie in Argumenten oder Ausgabe (henemm-infra#393). Die Software-Tests laufen mit pytest-xdist parallel (`FR_PRUEF_PROZESSE`, Vorgabe `auto`), wenn `FR_PYTHON` es hat. Sind die Pflichtprüfungen der eingebundenen Software-Version auf GitHub schon grün (`FR_CI_NACHWEIS`, Vorgabe 1, #403), entfällt die Testrunde auf dem Server ganz; ohne Nachweis läuft sie wie beschrieben. Der Lauf endet mit Exit 1, der Stand wird nicht gemerkt.

Warnungen im Plan sperren nie, weder im Bau noch im Schreibweg (dort stehen neue Warnungen als Hinweise in der Antwort). Die Tests in `tests/` des Reisen-Repos laufen danach weiter, sperren aber nicht: Sind sie rot, steht „Warnung: Tests des Reisen-Repos rot (sperren nicht)“ im Protokoll, und der Betrieb bekommt je Commit einmal eine Nachricht (`normal`; Merker `<FR_DIENST>/veroeffentlichen-warnung`).

**Rot-Datei:** Ein roter Stand steht in `<FR_DIENST>/veroeffentlichen-rot`, Zeilen `schluessel=wert`: `commit` (der rote Stand), `art` (`software` oder `reise`), `reisen` (die roten Reisen, durch Komma), `seit` (Beginn der Rot-Phase, UTC), `gemeldet` (`1`, wenn der Alarm an den Betrieb raus ist), `umgebung` (Fingerabdruck der Prüfumgebung: installierte Bibliotheken, Python, Node, Playwright), `geprueft` (Zeit der letzten Prüfung, Sekunden seit 1970) und `tests` (die ersten roten Tests mit der ersten Fehlerzeile; der Alarm nennt sie). Eine Rot-Phase reicht vom ersten roten Lauf bis zum nächsten ganz grünen; ein neuer roter Commit ändert `commit`, `art` und `reisen`, `seit` und `gemeldet` bleiben. Ein ganz grüner Lauf löscht die Datei.

**Kein Wiederholen ohne Änderung:** Kommt der nächste Lauf auf denselben roten Commit, steht „Known red state …, skipped“ (Bekannter roter Stand) im Protokoll: keine Tests, kein Bau, Exit 0, aber **kein Stempel und kein Heartbeat** (Rot ist kein fachlicher Erfolg). Neu geprüft wird bei einem neuen Commit, mit `--immer` und von selbst (#203): sofort, wenn sich die Umgebung geändert hat (ein Fehler, den eine Installation behebt, heilt so ohne Eingriff), und bei roter Software zusätzlich, wenn die letzte Prüfung länger als `FR_ROT_NEU_PRUEFEN_MINUTEN` (Vorgabe 60) zurückliegt; eine rote Reise ist ein Inhaltsfehler und wartet auf einen neuen Commit. `seit` und `gemeldet` bleiben dabei, es gibt also keinen zweiten Alarm. Eine Rot-Datei ohne Fingerabdruck (von vor #203) wird einmal geprüft. Ein Baufehler, der nur durch etwas anderes außerhalb des Repos verschwindet, braucht `--immer`. Infrastrukturfehler werden dagegen nicht gemerkt und vom Timer wiederholt: Vorspulen oder Submodul scheitern, `deploy.sh` endet mit Exit 1 (dann endet auch die Schleife über die Reisen sofort).

**Alarm:** Ist ein Stand seit `FR_ROT_MELDEN_NACH_MINUTEN` Minuten rot (Vorgabe 30, Einstellungen), geht bei jedem Lauf, der das Rot kennt (auch beim Überspringen), die Alarmprüfung los: einmal je Rot-Phase `high` an den Betrieb („Veröffentlichen seit … Minuten rot“, mit Art, Reisen und Commit). Kommt die Nachricht nicht an, bleibt `gemeldet=0` und der nächste Lauf versucht es wieder. Bei roten Reisen legt `engine/waechter.py rot-melden --reisen <a,b> --seit <seit>` dazu je Reise eine Meldung an deren Organisator:innen an (sie sehen sie im Konnektor); der Schlüssel enthält Reise und `seit`, darum kommt sie je Phase nur einmal. Bei roter Software geht nur der Alarm an den Betrieb.

**Konvention für `tests/` des Reisen-Repos:** Inhaltsschnappschüsse (feste Warnungslisten, Tageszahlen, Summen, Bildanzahlen) im `tests/` des Reisen-Repos sperren nicht und gehören dort gekennzeichnet oder entfernt: Jede Änderung über den Schreibweg kann sie rot machen, ohne dass etwas kaputt ist. Das gilt ebenso für den Workflow „Software nachziehen“ (#168): Er sperrt nur bei roten `engine/tests` oder einer Reise, die nicht baut; rote `tests/` sind dort eine Warnung im Lauf. Was wirklich sperren soll, gehört als Regel des Baus in die Software (eigenes Issue, gemessen an `docs/adr/0001-kern.md`), nicht als Schnappschuss.

**Reisen aus dem Reisespeicher (Stufe 3, #348):** Für die Reisen in `FR_SPEICHERREISEN` läuft vor `git fetch` ein eigener Teil, der kein Netz braucht (kein `git fetch`, kein `gh`, kein `ls-remote`); ist GitHub nicht erreichbar, sind sie trotzdem veröffentlicht, und der Lauf endet nicht mit Fehler, nur Software und Git-Reisen warten (Stufe 5, #350; Abschnitt „Umschaltung einer Reise“, Punkt GitHub-Ausfall). Ohne Liste entfällt er ganz, und ein gescheitertes `git fetch` ist wie bisher ein Fehler. Je Reise mit Eintrag im Speicher (ohne Eintrag: Hinweis, übersprungen; ohne Stempel `.gebaut`, in Git und ohne gültigen Stempel des Vergleichslaufs: Hinweis, übersprungen, Sperre bei der ersten Umschaltung):

- **Bauen,** wenn ihre Stand-Nummer im Speicher nicht die der Seite ist (`daten.json`), mit `--immer` oder ohne Stempel `<FR_DIENST>/reise-stand/<reise>.gebaut`. Gebaut wird aus `<FR_DIENST>/bau/reisen/<reise>`, außerhalb des Git-Bauordners: `engine/reisespeicher.py materialisieren` ersetzt den Ordner und hält die Nummer in `<reise>.stand` daneben fest; die Seite trägt genau diese Nummer, auch wenn währenddessen jemand schreibt (der nächste Lauf baut den neueren Stand). Dann `deploy.sh <reise>` und Freischalten wie bei Git-Reisen. Wann gebaut wird, folgt aus der Nummer, nicht aus `git diff`.
- **Software-Wechsel:** Nennt der Stempel `.gebaut` („`<nummer> <software-kennung>`“, Kennung = Stand des Submoduls `frieda/`) eine andere Software, stellt `engine/neu.py nachziehen-speicher <reise> <ordner>` die Reise vorher um: materialisieren, `neu.py nachziehen`, Probebau mit der neuen Software, dann genau ein Vorgang (Person „Software-Nachziehen“, Werkzeug `nachziehen`, Grund = Meldungen der Umstellung). Nichts umzustellen: kein Vorgang; Probebau rot: nichts geschrieben, die Reise ist rot; schreibt der Schreibweg dazwischen, beginnt es neu, höchstens dreimal. Übernommen wird eine neue Software erst, wenn der Git-Teil sie geprüft und vollständig veröffentlicht hat (Datei `veroeffentlicht`); bis dahin bleibt jede Reise mit älterem Stempel auf ihrem letzten guten Stand, auch für neue Inhalte (Hinweis im Protokoll). Hat der Git-Teil die Software gewechselt, startet der Lauf danach gleich noch einmal (`veroeffentlichen-nochmal`), und der Speicher-Teil stellt um. Zeitgeber ist der vorhandene Lauf alle 5 Minuten; es gibt keine eigene Einheit und keinen Handschritt.
- **Ergebnis:** Gelungen: Stempel `.gebaut`, `…lauf.json` `veroeffentlicht` mit der Nummer aus dem Speicher. Bau gescheitert (Exit 2): `…lauf.json` `fehlgeschlagen` mit Grund, die Reise steht in der Rot-Datei (`art=reise`, `reisen=` nennt die roten Reisen beider Quellen) und meldet sich über den Alarm (unten), ohne Issue vom Server; die anderen Reisen laufen weiter. Störung (Speicher nicht lesbar, `deploy.sh` Exit 1): der Lauf endet mit 1, nichts wird gemerkt. Stempel und Heartbeat gibt es nur, wenn beide Teile fachlich erfolgreich waren.

`FR_WURZEL=<Bauordner> betrieb/deploy.sh <reise>` (sonst von `veroeffentlichen.sh` aufgerufen) baut, führt die Tests der Software aus (`engine/tests`, außer der Stand ist schon geprüft) und kopiert die Seite nach `<FR_SEITEN>/<reise>/`. Exit-Codes: 0 gelungen, Exit 2 Bau dieser Reise gescheitert (vor jeder Wirkung, die Seite bleibt auf dem letzten guten Stand), 1 alles andere (`FR_WURZEL` fehlt, Ordner nicht auf `main`, Reise oder Ordner fehlt, ungesicherte Änderungen, Tests rot, Dienste nicht bereit). Es legt die Ablage der Reise an und kopiert den Code der Dienste nach `<FR_DIENST>/`: über `betrieb/ersetzen.sh` nur geänderte Dateien, jede erst als Temp-Datei und dann umbenannt, damit ein gleichzeitiger Schreibvorgang kein Modul fehlend oder halb geschrieben vorfindet (#489). Die Liste der Module steht im Skript, ein Test prüft sie gegen die Importe. Bei geändertem Code startet es die Dienste neu (`sudo -n systemctl restart`). Am Ende prüft es Seite, Rückmeldedienst und Konnektor.

## Neue Reise freischalten

Ohne Handarbeit (`docs/neue-reise.md`): Nach dem Veröffentlichen ruft `veroeffentlichen.sh` für jede Reise `freischalten.sh <reise>` auf.

- **Neue Reise:** Sie bekommt einen nginx-Baustein aus `vorlagen/nginx-reise.conf` mit einem neuen Zufalls-Token (root, 640). Dann `nginx -t`; bei einem Fehler wird der Baustein wieder entfernt. Danach lädt nginx neu. Bis die neuen Pfade gelten, vergeht ein Moment; die Prüfung des neuen Links versucht es deshalb bis zu zehnmal im Sekundenabstand.
- **Prüfung:** Seite und `api/gesund` müssen mit 200 antworten. Eine 429 kommt von der Anfragebegrenzung in nginx (je IP, gemeinsam für die API aller Reisen; der Server fragt sich selbst von außen ab), nicht von der Reise: Die Prüfung wartet dann 5 s und fragt erneut, bis zu sechsmal (`FS_429_WARTEN`, `FS_429_VERSUCHE`, #198). Vorher blieben neue Reisen dadurch ohne Verknüpfung mit dem Konto, bis ein späterer Lauf sie freischaltete.
- **Link:** Der Link zur Seite kommt nach `seiten.json` (für `meine_reisen`).
- **Vorgemerkte neue Reisen:** Neue Reisen aus der App merkt der Konnektor in `<FR_KONNEKTOR>/neue-reisen-ausstehend.jsonl` vor (den Dienstordner darf der Konnektor nicht beschreiben). Das Veröffentlichen stellt sie zu (`betrieb/zustellen.py`), sobald die Seite online ist: Verknüpfung des Kontos mit der Reise, Einladungen per Mail und die Meldung „neue Reise“. Links für die Claude-App gibt es nicht mehr (#421).
- **Ohne Root-Rechte:** Der Schreibweg stößt das Veröffentlichen aus einem Dienst mit `NoNewPrivileges` an; darin geht kein `sudo`. Dieser Lauf baut und veröffentlicht, schaltet aber nicht frei und stellt nicht zu: Die Reisen kommen nach `<FR_DIENST>/freischalten-ausstehend`, und der nächste Lauf des Timers (höchstens 5 Minuten später) schaltet sie frei, auch wenn es sonst nichts Neues gibt (#465). Spult so ein Lauf die Software vor, merkt `deploy.sh` die fälligen Neustarts der Dienste in `<FR_DIENST>/neustart-ausstehend` vor, und der nächste Lauf mit Root-Rechten startet sie neu, noch vor dem Abruf von GitHub; scheitert ein Neustart, bleibt nur dieser vorgemerkt (#494). Vorher stand nur „please run: sudo systemctl restart …“ im Protokoll, und die Dienste liefen bis zum nächsten Software-Wechsel mit altem Code. `freischalten.sh` selbst bricht ohne Root-Rechte mit einer eigenen ERROR-Zeile ab; vorher las es das gescheiterte `sudo test -e` als „Baustein fehlt“ und hätte der Reise einen neuen Link angelegt.

Von Hand: `freischalten.sh <reise>` für die Seite (die Option `--person` ist mit den Links für die Claude-App entfallen). Links stehen nie im Protokoll, im Repo, in Issues oder Nachrichten.

## Warteliste (#382)

Interessenten tragen sich auf `<FR_BASIS>/warteliste` ein und bestätigen ihre Adresse über den Link aus der Mail
(`/warteliste/bestaetigen/<wort>`). Ablauf und Grenzen: `docs/konten.md`, „Warteliste“. Neue Einstellungen gibt es nicht:
Absender, SMTP und Links kommen wie bei den Anmeldecodes aus `FR_ABSENDER`, `FR_SMTP_*` und `FR_BASIS`; fehlt die
Mail-Einrichtung, lehnt die Seite ab und speichert nichts.

- Jeder bestätigte Eintrag erzeugt eine Meldung an die Betreiber (wie die Bitte „Reisen anlegen“, in der Claude-App bei
  `meine_reisen`).
- `python3 engine/konten.py warteliste` listet die bestätigten, noch nicht freigegebenen Einträge (älteste zuerst) und die
  Zahl der unbestätigten.
- `python3 engine/konten.py freigeben <email>` (oder der Knopf im Abschnitt „Warteliste“ auf Mein Konto, nur mit Recht
  `betreiber`) schickt die Mail „Du bist dabei“ und gibt das Recht „Reisen anlegen“, auch Adressen mit Konto. Scheitert
  die Mail, meldet der Befehl `ERROR` (Exit 2) und die Seite den Fehler; der Eintrag bleibt wartend, ein zweiter Versuch geht.
- nginx: `location = /warteliste` (Drossel wie `/anmelden`, weil sie Mails auslöst) und
  `location ^~ /warteliste/bestaetigen/` (Drossel wie Konto) in `vorlagen/nginx-konnektor-orte.inc`; neue Orte dieser
  Datei installiert das Hilfsprogramm `nginx-orte-installieren` beim Veröffentlichen selbst (#445, siehe „nginx-Bausteine
  abgleichen“ unten), vorher ist `/warteliste` auf dem Server nicht erreichbar.

## Meldungen an den Betreiber (#530)

Fehler, Wünsche und Fragen zu Frieda selbst melden Personen mit Konto in der Claude-App (Konto-Werkzeug `report_to_frieda`,
intern `an_frieda_melden`). Die Meldung liegt in der Kontendatenbank (Tabelle `betreiber_meldungen`); jedes nicht
gesperrte Konto mit dem Recht `betreiber` bekommt eine Mail in seiner Sprache, „Antworten“ geht an die Adresse der Person
(Reply-To), Absender bleibt `FR_ABSENDER`. Neue Einstellungen gibt es nicht.

- Höchstens 10 Meldungen je Konto und Tag (gemeinsames Mailkontingent); abgelehnte zählen nicht.
- Scheitert eine Mail, bleibt die Meldung gespeichert; im Protokoll des Konnektors steht
  `operator report <nr>: mail failed: <Schlüssel>`. Wiederfinden: `meine_reisen` eines Betreiber-Kontos (offene Meldungen,
  die letzten 20) oder `python3 engine/konten.py meldungen [--alle]`.
- Abhaken: `python3 engine/konten.py meldung-erledigt <nr> <issue>` mit dem Verweis auf das Issue. Issues zu Meldungen
  entstehen nur im privaten Reisen-Repo der Instanz, nie im öffentlichen Repo (Name, Adresse und Text sind Personendaten).
- Konto löschen entfernt die Meldungen und ihre Zählzeilen; der Export der Person enthält sie (ohne Verweis auf das Issue).

## Reise-Stand (Epic #223)

Jede Reise trägt eine fortlaufende Nummer, den **Reise-Stand**: die Zahl der Commits auf `main`, die `reisen/<reise>/` ändern (`engine/stand.py`). Jeder gesicherte Schreibvorgang erhöht sie um 1, ein Software-Update (Submodul) lässt sie stehen; weil `main` nur wächst, enthält Stand 43 alles aus Stand 42. In einem flachen Klon fehlt die Nummer (wie die des Releases). Der Bau legt sie mit den letzten zehn Änderungen (Zeit, Person, was; Person aus der Zeile `Frieda-Person:` des Schreibwegs, sonst der Autor des Commits) in die Seite (`daten.reise_stand`); eine Bauzeit steht nicht darin, gleicher Inhalt gibt weiter dieselbe Seite.

Weg eines Stands: **gesichert** (Schreibweg) → **wird gebaut** → **veröffentlicht** (die Seite liegt auf dem Server) → **auf dem Gerät** (nur die Person sieht das, im Fuß). Scheitert der Bau, ist der Zustand **fehlgeschlagen** mit dem Grund (Meldungen von `bauen.py`), und der bisherige Stand bleibt sichtbar; rote Prüfungen der Software melden sich ebenso, mit den roten Tests. Die Dateien in `<FR_DIENST>/reise-stand/` haben je einen Schreiber: `<reise>.gesichert.json` der Schreibweg, `<reise>.lauf.json` `veroeffentlichen.sh` (Zustand, Nummer, Zeit des Sicherns, seit wann, Dauer, Grund). Veröffentlicht ist, was `<FR_SEITEN>/<reise>/daten.json` nennt.

Abgefragt wird nur auf dem Server: Der Rückmeldedienst antwortet unter `api/stand` (die Seite; der Service Worker lässt `api/` nie über seinen Speicher), der Konnektor mit `veroeffentlichung_pruefen` (`publish_status`, `docs/konnektor.md`). Zeiten stehen dort als UTC mit `Z`; die Seite zeigt sie in der Ortszeit des Geräts, der Konnektor in der Zeitzone der Person mit Angabe der Zone (sonst `FR_ZEITZONE`, Vorgabe UTC; #227).

**Zeitziel 2 Minuten** vom Sichern bis zur Veröffentlichung (Product Owner, E3, 2.11.2026; #230). Gemessen wird je Reise: `veroeffentlichen.sh` schreibt nach dem Bau „Published <reise> state <n>, <s> s after saving.“ ins Protokoll, über dem Ziel als Warnung, und die Dauer nach `<reise>.lauf.json`. Ein Neubau eines Stands, der schon auf der Seite war (`--immer`, Software-Wechsel, Umschaltung auf den Speicher; Merker `<reise>.seite`), ist keine Wartezeit: „Published <reise> state <n> again (already on the page).“, ohne Dauer (#465); `veroeffentlichung_pruefen` zeigt sie gegen das Ziel, auch während ein Stand noch wartet. Ursache der 15 Minuten vom 2.11.2026 (Baustein um 09:32 gesetzt, um 09:47 sichtbar), aus dem Ablauf des Skripts: Jeder neue Commit auf `main`, auch ein reiner Inhaltsstand, ließ die ganze Prüfung der Software laufen (`engine/tests` mit Browsertests, auf der Instanz mehrere Minuten) und danach alle Reisen bauen; fand der Anstoß des Schreibwegs die Sperre eines laufenden Timer-Laufs belegt, wurde er übersprungen, und der Stand wartete bis zum nächsten Timer-Lauf (5 Minuten) samt dessen voller Prüfung. Seitdem:

- Ein **reiner Inhaltsstand** (seit dem zuletzt ganz veröffentlichten Stand nur Änderungen unter `reisen/`) baut nur die geänderten Reisen (und die zuletzt roten, damit ihr Rot bestehen bleibt, bis ihr Bau gelingt) und überspringt die Prüfungen der Software, die für genau diese Software schon grün waren (`FR_GEPRUEFT` auf den Stand gesetzt).
- Ein **Software-Wechsel** (alles außerhalb von `reisen/`, auch das Submodul, oder ohne bekannten Stand, oder `--immer`) prüft weiter vollständig und baut alle Reisen. Nur dann laufen die Tests des Reisen-Repos, nach dem Bauen, damit sie keinen Stand aufhalten.
- Ein Anstoß, der die Sperre belegt findet, legt `<FR_DIENST>/veroeffentlichen-nochmal` an; der laufende Lauf startet am Ende gleich noch einmal, statt auf den Timer zu warten.

## Anstoß „Veröffentlichen“ von der Seite

Die Seite kann nur holen, was auf dem Server liegt. Der Fuß jeder Seite fragt auf „Auf Neueres prüfen“ zuerst den Server (Update des Service Workers): Liegt dort ein neuer Stand, heißt der Knopf „Jetzt aktualisieren“ und übernimmt ihn (mit Rückfall: feuert der Wechsel nicht, lädt die Seite nach 4 Sekunden trotzdem neu). Ist nur `main` der Software neuer, nennt der Fuß die Zahl der Stände und sagt, dass sie noch nicht auf dem Server sind. Organisator:innen (angemeldet) bekommen dazu „Veröffentlichen anstoßen“: Der Rückmeldedienst legt `<FR_ABLAGE>/_anstoss.json` an (Zeit, Reise, Person; ein Anstoß gilt, bis er abgeholt ist).

Im Software-Klon (#454) stößt das nur einen Lauf an: Der nächste Lauf von `veroeffentlichen.sh` (Timer, höchstens 5 Minuten) holt den neuesten Stand von `main`, prüft ihn und veröffentlicht ihn wie oben, schreibt `ok: true` nach `<FR_ABLAGE>/_anstoss-ergebnis.json` und löscht den Anstoß; es gibt keinen Workflow und kein `gh`, also auch keine Voraussetzung an Anmeldungen. Die Seite zeigt „Stand noch nicht auf dem Server“, bis der Lauf grün durch ist. Mit Push-Nachrichten bekommen alle eine Nachricht, sobald das neue Release online ist; Tippen darauf öffnet die Seite mit `?aktualisieren=1`, und die Seite übernimmt den neuen Stand selbst. Vor dem Umzug startete der Lauf stattdessen den Workflow „Software nachziehen“ des Reisen-Repos.

## Push-Nachrichten

`engine/push.py dienst` (`<instanz>-push.service`) stellt Push-Nachrichten zu (Issue #21, Kanal `push` in `docs/waechter.md`). Er läuft mit `FR_PYTHON`, weil der Versand `pywebpush` braucht (`engine/requirements.txt`; bei einer bestehenden Instanz einmal `engine/.venv/bin/pip install -r engine/requirements.txt`), und lädt seinen Code aus `<FR_DIENST>` (`PS_MODULE` in `deploy.sh`, Neustart bei geändertem Code, wenn die Unit eingeschaltet ist). Alle 20 Sekunden liest er, was in den Reisen neu ist (`meldungen.jsonl`, `eingang.jsonl`, `aufgaben.json` der Ablage und das Release im Fuß der veröffentlichten Seite), merkt sich den Stand in `konten.db` (`push_stand`; beim ersten Lauf nur merken) und stellt die Nachrichten aus der Warteschlange (`push_warteschlange`) zu, außerhalb der Ruhezeit der Person. Was 36 Stunden nicht zugestellt werden konnte, fällt weg; ein Abo, das der Push-Dienst des Browsers nicht mehr kennt (404, 410), wird gelöscht.

- **Schlüssel:** Das VAPID-Schlüsselpaar legt der erste Start an (`konten.db`, Tabelle `push_schluessel`); `engine/push.py schluessel` zeigt den öffentlichen. Ihn bringt „Mein Konto“ für den Schalter mit (`data-schluessel`); ohne ihn bietet die Seite keine Benachrichtigungen an. Wird der Schlüssel ersetzt, müssen alle Geräte neu einschalten.
- **Geräte:** Abos je Gerät in `konten.db` (`push_abos`: Adresse beim Push-Dienst, Schlüssel, Reise und Adresse der Seite, Zeitzone), höchstens 10 je Konto. Sperren, Löschen und „Auf allen Geräten ausschalten“ (Mein Konto) entfernen sie.
- **Link der Nachricht:** die Adresse der Seite aus einem Abo derselben Reise, sonst aus `seiten.json` im Ordner des Konnektors (`FR_KONNEKTOR`).
- **Kontakt:** `FR_BASIS` aus `konten.env` steht als Absender in der VAPID-Unterschrift.
- **Probe:** `FR_KONTEN=… RM_ABLAGE=… engine/.venv/bin/python <FR_DIENST>/push.py probe <email>` schickt eine Nachricht an alle Geräte eines Kontos. Protokoll: `journalctl -u <instanz>-push`.
- **Frieda-App (Entscheidung A, 2.11.2026):** Ein- und ausgeschaltet wird je Gerät auf „Mein Konto“ (`engine/app/konto.js`, POST `/konto` mit `aktion=push_an` oder `push_ab`, Sitzung und Origin wie jede Änderung; Antwort 204). Das Abo gehört zu keiner Reise (`reise` leer, `seite` = `<FR_BASIS>/konto`) und bekommt die Nachrichten aller Reisen; gezeigt werden sie vom Worker `/sw.js` der Frieda-App (Scope `/`, nur Push, kein Abfangen, kein Speichern). Manifest, Worker und Skript liefert der Konnektor aus `<FR_DIENST>/app/` (`deploy.sh` kopiert `engine/app/`); der server-Block braucht dafür die Orte `/manifest.webmanifest`, `/sw.js` und `/konto.js` (Baustein `<instanz>-konnektor-orte.inc`, `wege_pruefen` prüft sie). Der Fuß der Reiseseite verweist nur auf „Mein Konto“; `api/push` der Reiseseite bleibt für ältere Abos.
- **iPhone und iPad:** Push gibt es nur in der App vom Home-Bildschirm (iOS 16.4 und neuer). Im Browser zeigt „Mein Konto“ die drei Schritte: Teilen, „Zum Home-Bildschirm“, Frieda öffnen und dort einmal anmelden (die App hat eigene Cookies).

## Wächter

`betrieb/waechter.sh` läuft täglich und ruft `engine/waechter.py lauf` auf (`docs/waechter.md`). Es berücksichtigt nur Reisen mit Baustein `waechter` und Status `fest` oder `unterwegs`, nie zur Löschung vorgemerkte Reisen. Hat es etwas zu melden, geht eine Sammelnachricht an den Betreiber; ein Fehler (auch beim Löschen, unten) wird dringend gemeldet. Danach schreibt es die Schnappschüsse der Konten (`engine/konten.py sichern`) und des Reisespeichers (`engine/reisespeicher.py sichern`), siehe „Sicherung“; schlägt einer fehl, kommt je Sicherung eine dringende Meldung, die andere Sicherung läuft trotzdem, und der Stempel bleibt aus.

**Löschen von Reisen (#381):** Danach ruft es `engine/waechter.py loeschen` auf. Für jede Reise, deren Schonfrist abgelaufen ist (`konten.faellige_loeschungen`), und jede Reise des Löschprotokolls, die nach dem Rückspielen einer alten Sicherung wieder im Speicher, in der Ablage oder im Webordner steht: erst ein Schnappschuss (`reisespeicher.sichern`), dann `reisespeicher.reise_entfernen` (alle Vorgänge und Versionen in einer Transaktion, Ablagedateien nur ohne Verweis einer anderen Reise), dazu `<FR_ABLAGE>/<reise>/`, `<FR_SEITEN>/<reise>`, `<FR_DIENST>/bau/reisen/<reise>`, die Stempel `<FR_DIENST>/reise-stand/<reise>.*` und der Link in `<FR_KONNEKTOR>/seiten.json` (der nginx-Baustein des geheimen Links bleibt und liefert 404; entfernen kann ihn nur der Betreiber mit Root-Rechten); nach jeder Reise `pruefen` über alle verbleibenden Reisen. Ist es nicht grün, bricht der Lauf ab, meldet dringend und entfernt keine weitere Reise. Am Ende `verdichten` (`wal_checkpoint(TRUNCATE)` und `VACUUM`) und ein frischer Schnappschuss, dann trägt `konten.loeschung_abschliessen` die Reise ins Löschprotokoll ein (nur Kennung und Datum). Das Veröffentlichen baut vorgemerkte Reisen nicht und entfernt ihren Webordner sofort (`engine/konten.py vorgemerkt`); nach dem Zurückholen baut es sie wieder. Die Server-Sicherungen enthalten Gelöschtes bis zu ihrer Rotation; Ziel sind höchstens 30 Tage.

Die Skripte setzen daraus die Umgebung der Software (`RM_ABLAGE`, `KN_SEITEN`, `KN_BASIS`, dazu `FR_KONNEKTOR`; die Unit des Konnektors zusätzlich `KN_SCHREIBDIENST`; ältere Units setzen noch `KN_ZUGAENGE`, dessen Ordner gilt dann als `FR_KONNEKTOR`, #421). Ausdrücklich gesetzte Werte bleiben. Fehlt etwas, etwa bei einem Aufruf von Hand wie `python3 engine/rueckmeldungen.py liste <reise>` in der Wurzel des Reisen-Repos, leitet `engine/instanz.py` die Ordner nach derselben Ordnung ab, notfalls aus der Einstellungsdatei. Die Software selbst kennt keine Instanz, ihre letzte Vorgabe ist `/srv/frieda`.

**Meldeweg:** `FR_MELDEN` ist eine ausführbare Datei der Instanz (ein relativer Pfad gilt ab der Wurzel des Reisen-Repos), aufgerufen als `<befehl> <normal|high> <betreff> <text> [erledigt]`. `erledigt` heißt: Das ist ein reiner Bericht, es ist nichts zu tun. Fehler kommen ohne `erledigt` und sollen offen bleiben, bis jemand sie ansieht. Wie die Nachricht ankommt (Mail, Telegram, eine Warteschlange), entscheidet die Instanz in ihrem Skript.

Die Stufen haben eine feste Bedeutung (#446): `high` ist ein Alarm und nur für Ausfälle, bei denen der Betreiber jetzt handeln muss und kann; `normal` ist etwas zu tun ohne Ausfall (die erste Instanz macht daraus ein Issue im Reisen-Repo); `normal erledigt` ist ein Bericht. Alarme gibt es an vier Stellen, begründet in `ALARMSTELLEN` (`engine/tests/test_betrieb.py`): Wächter-Lauf gescheitert, Sicherung der Konten gescheitert, Sicherung des Reisespeichers gescheitert (alle `waechter.sh`) und Veröffentlichen länger als `FR_ROT_MELDEN_NACH_MINUTEN` rot (`veroeffentlichen.sh`). Jeder Alarm kommt einmal je Störung: Der Wächter legt nach erfolgreicher Zustellung den Merker `<FR_DIENST>/alarm-<teil>` an (`waechter`, `sicherung-konten`, `sicherung-reisen`) und löscht ihn, sobald der Teil wieder gelingt; kommt der Alarm nicht an, versucht es der nächste Lauf wieder. Das Veröffentlichen meldet einmal je Rot-Phase. Wie lange eine Störung anhält, zeigt die Überwachung (Stempel `waechter-erfolg`, Teil-Checks in `monitor.sh`, Heartbeat der Sicherung), nicht ein wiederholter Alarm.

## Seiten prüfen (angemeldet, im echten Browser)

Die Reiseseiten verlangen eine Anmeldung (E-Mail und Code). Für Prüfungen der veröffentlichten Seiten gilt der übliche Weg von Playwright: ein eigenes Konto mit den geringsten Rechten, die Sitzung außerhalb des Browsers erzeugen und als Cookie einsetzen (`storageState`). Die Anmeldung selbst wird nicht nachgespielt und bekommt keine Hintertür. `betrieb/pruefsitzung.py <datei.json> [--stunden 2]` legt beim ersten Mal das Konto `pruefung@<Adresse der Seiten>` an (kein Mitglied einer Reise, sieht nur, was eine fremde Person mit dem Link sieht), stellt eine kurze Sitzung aus und schreibt sie als storageState (Rechte 600, nie ins Repo). Der Aufruf geschieht als Dienstbenutzer mit den Werten der Instanz (`RM_SEITEN` oder `FR_KONTEN`, `FR_KN_ADRESSE`). Im Browser: `browser.newContext({storageState: "<datei>"})`, dann die Adresse der Reise mit dem geheimen Pfad öffnen. Das Prüfkonto liest damit alle Reiseseiten; schreiben darf es nirgends.

## Überwachung

Nach fachlichem Erfolg berühren die Läufe Stempel in `<FR_DIENST>/`: `veroeffentlichen-erfolg` (nichts Neues oder alles veröffentlicht; nicht bei einem roten oder übersprungenen roten Stand) und `waechter-erfolg`. Ein roter Stand meldet sich selbst: nach `FR_ROT_MELDEN_NACH_MINUTEN` Minuten (Vorgabe 30) einmal je Rot-Phase an den Betrieb, bei roten Reisen auch an deren Organisator:innen (Veröffentlichen, Rot-Datei `<FR_DIENST>/veroeffentlichen-rot`). ## Neue Instanz einrichten

1. **Server:** Benutzer für die Dienste, nginx mit HTTPS für die Adresse, Python 3, `git`, `rsync`, `flock`, Node 22 (Browser-Prüfung in den Tests) und `gh`, als dieser Benutzer angemeldet (Credential-Helfer für `git push` des Schreibwegs). Claude Code ist auf dem Server nicht nötig.
2. **Reisen-Repo:** neues privates Repo mit der Software als Submodul:
   ```
   git submodule add https://github.com/henemm/frieda-reist frieda
   ln -s frieda/engine engine
   mkdir -p reisen betrieb && cp frieda/betrieb/einstellungen.beispiel betrieb/einstellungen.env
   ```
   Werte eintragen; ein Meldeskript ist optional. In `.gitignore`: `dist/`, `reisen/*/medien/karte`.
   **Software nachziehen:** `cp frieda/betrieb/software-nachziehen.yml .github/workflows/` (dazu ein `tests.yml`, das `python -m pytest -q -rs engine/tests tests` ausführt). Der Workflow braucht die Rechte `contents: write` und `issues: write`, die er selbst anfordert. In den Einstellungen des Repos müssen Actions erlaubt sein, mit Schreibrechten für `GITHUB_TOKEN`. Alle 30 Minuten zieht er das Submodul auf den neuen Stand von `main` der Software, als Commit des Bots. Das Tor ist dasselbe wie beim Veröffentlichen: Sperren können nur die Tests der Software (`engine/tests`) und der Bau jeder Reise; rote Tests des Reisen-Repos (`tests/`) sind nur eine Warnung im Lauf. Sperrt das Tor, legt er ein Issue mit dem Label `software-nachziehen` an. Die Vorlage wird nur einmal kopiert: Sie ermittelt den Stand, setzt das Submodul und ruft `frieda/betrieb/software-nachziehen.sh` aus dem neuen Stand auf; der Ablauf kommt mit der Software (Ablauf unten).

   **Ablauf von `betrieb/software-nachziehen.sh`** (#250, auf dem Runner im Klon des Reisen-Repos):
   1. **Umstellen:** `neu.py nachziehen` für jede Reise mit `reise.json`, in jedem Lauf, auch ohne neuen Software-Stand (idempotent). So werden auch Reisen umgestellt, deren Software schon früher nachgezogen wurde. Fehlt in `reise.yaml` das Feld `sprache` (oder ist es leer), trägt es `sprache: de` ein, was für diese Reisen bisher galt; ein vorhandener Wert bleibt, auch ein unbekannter (#267). Ein offener Punkt („OFFEN …“) sperrt nicht, er erscheint als Warnung. Reisen aus `FR_SPEICHERREISEN` (gelesen aus `betrieb/einstellungen.env`) überspringt der Workflow hier und im Tor: Sie stellt der Server beim Veröffentlichen selbst um (#348), ihre Git-Kopie ist veraltet. Der Workflow liest `FR_SPEICHERREISEN` wie der Server: ein Wert aus der Umgebung gilt vor der ersten Zeile in der Einstellungsdatei.
   2. **Nichts geändert** (weder Submodul noch Reisen): Ende, grün, kein Commit.
   3. **Tor:** `engine/tests` nur bei neuem Software-Stand, der Bau jeder Reise in jedem Lauf mit Änderung; `tests/` des Reisen-Repos nur Warnung.
   4. **Übernehmen:** ein Commit des Bots mit Submodul und umgestellten Reisen, erste Zeile „Software auf Stand X (automatisch)“ oder „Reisen auf den Stand der Software umgestellt (automatisch)“, darunter die Liste der Commits und die Meldungen der Umstellung je Reise.
   5. **Wettlauf mit dem Schreibweg:** Scheitert der Push, setzt das Skript auf `origin/main` zurück, setzt das Submodul erneut, stellt neu um, prüft die Reisen neu und committet neu; die Tests der Software (`engine/tests`) laufen nur einmal je Lauf, ihr Ergebnis gilt für jeden Versuch (der Stand der Software bleibt derselbe, sonst wird das Fenster für den Wettlauf so lang wie die Testzeit, #460). Höchstens drei Versuche, nie erzwungen; scheitern alle, endet der Lauf rot ohne Issue, und der nächste Lauf versucht es wieder.
   6. **Tor rot:** Ohne offenes Issue `software-nachziehen` entsteht eins, und der Lauf endet rot (GitHub mailt). Mit offenem Issue endet er mit einer Warnung und grün, ohne Commit; nennt das Issue den aktuellen Software-Stand noch nicht, bekommt es einen Kommentar mit Stand und Lauf. Das offene Issue ist die Meldung, bis es geschlossen ist.

   Fehlt das Skript im gesetzten Stand (Submodul älter als #250), endet der Lauf rot mit einem Hinweis im Protokoll. Konnektor und Schreibweg laufen nach dem Commit noch mit dem alten Code, bis der nächste Lauf von `veroeffentlichen.sh` sie neu startet (wenige Minuten); ein Schreibvorgang in diesem Fenster kann abgelehnt werden und gelingt danach.

   **Anstoß vom Server:** `veroeffentlichen.sh` fragt bei jedem Lauf mit `git ls-remote` nach `main` der Software (URL aus `.gitmodules`). Ist dieser Stand ein anderer als der eingebundene und noch nicht angestoßen, startet es `gh workflow run <FR_NACHZIEHEN_WORKFLOW>` und merkt Stand und Zeit in `<FR_DIENST>/nachziehen-angestossen` (nur nach Erfolg von `gh`). Für denselben Stand startet es erst wieder, wenn seit der gemerkten Zeit `FR_NACHZIEHEN_WIEDERHOLEN_STUNDEN` (Vorgabe 6) vergangen sind; so erzeugt ein rotes Tor eine Fehler-Mail je Software-Stand, nicht eine alle 5 Minuten. Scheitert `ls-remote` oder `gh`, ist das eine Warnung im Protokoll, das Veröffentlichen läuft weiter. Der Zeitplan von GitHub bleibt als Rückfallweg.
3. **Bauordner auf dem Server:** Klon des Reisen-Repos als Dienstbenutzer, `git submodule update --init`. Danach `python3 -m venv engine/.venv && engine/.venv/bin/pip install -r engine/requirements.txt`. `git fetch` muss ohne Rückfrage gehen. Lokale Dateien, die nicht ins Repo gehören (etwa `.claude/settings.json`), kommen in `.git/info/exclude`, sonst gilt der Ordner als belegt und das Veröffentlichen setzt aus.
4. **Einrichten:** `frieda/betrieb/einrichten.sh` prüft die Voraussetzungen. Es erzeugt Units und nginx-Bausteine in einem Ordner und zeigt die Befehle zum Aktivieren. Außerhalb dieses Ordners ändert es nichts. `--installieren` legt nach Rückfrage die Ordner an und kopiert Units und Bausteine nach `/etc`.
5. **nginx:** Im server-Block der Adresse `include <FR_NGINX_SNIPPETS>/<instanz>-*.conf;` eintragen, `nginx -t`, neu laden. Das bindet die Reiseseiten ein. Der Konnektor kommt mit einer eigenen Zeile `include <FR_NGINX_SNIPPETS>/<instanz>-konnektor-orte.inc;` in den Block seiner Adresse (gemeinsame Einstellungen in `<instanz>-konnektor.inc`). Beide enden bewusst auf `.inc`: Der Stern `<instanz>-*.conf` bindet sie nicht ein, sonst käme der Konnektor in jeden Block, der die Reiseseiten einbindet (etwa den einer zweiten Adresse), und die Orte stünden doppelt. Der Konnektor steht an der Wurzel der Adresse (#163):
   - `/` (Startseite: angemeldet Mein Konto, #41, sonst die Infoseite, #436), `/info/` (Infoseite für alle, #440, über den Ort der Bilder; `/info` leitet nginx selbst dorthin), `/mcp` (Claude-App), `/anmelden`, `/abmelden`, `/konto`, `/einladung/…`, OAuth (`/authorize`, `/token`, `/register`, `/.well-known/oauth-…`), `/kalender/…` (Abo), `/schrift/…`, `/info/…` (Bilder der Infoseite, #436; eine Instanz bindet den Ort nach dem Wechsel einmal neu ein, die Meldung „nginx blocks differ“ nennt den Befehl, bis dahin fehlen nur die Bilder), Favicon und App-Symbole, `/gesund`.
   - Reiseseiten und Konnektor teilen sich die Adresse: Die Sitzung (`__Host-frieda`) gilt nur dort, und die Reiseseite fragt mit ihr `api/ich`.
   - Kein `add_header Referrer-Policy "no-referrer"` im server-Block für diese Pfade: Der Dienst setzt `same-origin`, sonst schicken Browser `Origin: null` und jede Anmeldung scheitert an der Prüfung der Herkunft. Cache-Control und Content-Security-Policy setzt ebenfalls der Dienst.
   - Präfix-Orte (`^~`) und genaue Orte (`=`) gehen allgemeinen Regeln für Dateiendungen vor; Regeln mit `^~` oder `=` für dieselben Pfade im server-Block dürfen nicht stehen.
   - Die Links aus der Zeit vor den Konten (`/<token>`, früher `/<instanz>-mcp/<token>`) sind abgeschaltet (Frist 1.11.2026); die Vorlage hat keine Orte dafür, nginx antwortet 404.
6. **sudo** für den Dienstbenutzer, ohne Passwort und nur für diese Befehle:
   - `systemctl restart <instanz>-rueckmeldungen <instanz>-konnektor <instanz>-schreiben <instanz>-push`
   - `nginx -t` und `systemctl reload nginx`
   - `install`, `test`, `cat` und `rm` für Dateien in `<FR_NGINX_SNIPPETS>/<instanz>-*.conf`
7. **Erste Reise** leer anlegen: `engine/neu.py reise <reisen-ordner> --titel … --von … --bis … --person … --wer …` (nur Eckdaten und Personen, kein Inhalt; `docs/neue-reise.md`), nach `main` bringen, im Bauordner `FR_WURZEL=<Bauordner> frieda/betrieb/deploy.sh <reise>` (legt den Code der Dienste an). Danach `sudo systemctl enable --now <instanz>-rueckmeldungen <instanz>-konnektor <instanz>-schreiben <instanz>-push` und die beiden Timer, wie `einrichten.sh` sie nennt. Eine bestehende Instanz richtet den Push-Dienst nach: `pip install -r engine/requirements.txt`, `einrichten.sh --installieren` (neue Unit), sudo-Regel um `<instanz>-push` ergänzen, `enable --now <instanz>-push`.
8. **Prüfen:** `FR_WURZEL=<Bauordner> frieda/betrieb/veroeffentlichen.sh --immer` zeigt „Done: … is online“. `curl -s <FR_KN_ADRESSE>/.well-known/oauth-authorization-server` zeigt die Endpunkte unter derselben Adresse; in der Claude-App wird `<FR_KN_ADRESSE>/mcp` als Konnektor eingetragen, die Anmeldung läuft mit E-Mail und Code (`docs/konten.md`). `curl -s 127.0.0.1:<FR_SB_PORT>/gesund` antwortet `{"gesund": true}`.

**Zwei Instanzen auf einem Server** brauchen verschiedene `FR_INSTANZ`, `FR_SEITEN` (und damit Ablage und Dienstordner) und Ports. `einrichten.sh` bricht ab, wenn eine andere installierte Instanz dieselben Ports nutzt. Unit-Namen, nginx-Bausteine, Drossel-Zone und Sperrdateien tragen den Namen der Instanz. Jede Instanz braucht eine eigene Adresse (Host), weil ihr Konnektor an der Wurzel steht.

## Einheiten abgleichen (#260)

Die systemd-Einheiten in `/etc/systemd/system` entstehen aus `betrieb/vorlagen/`. Damit eine geänderte Vorlage nicht still
vom Server abweicht, vergleicht `veroeffentlichen.sh` nach jedem grünen Lauf `units.py pruefen` (erzeugt die Soll-Einheiten
mit `einrichten.sh --erzeugen` und vergleicht Zeile für Zeile; es ändert nichts). Bei einer Abweichung kommt genau eine
normale Meldung (Issue, kein Alarm), danach erst wieder bei einer anderen Abweichung (Merker `<FR_DIENST>/units-gemeldet`).
Ein Fehler im Abgleich stoppt das Veröffentlichen nie.

Ausgang von `units.py pruefen`: 0 alles gleich, 3 nur erlaubte Abweichungen, 4 auch gesperrte, 1 Fehler. Erlaubt sind nur
die Zeilen `Environment=FR_DIENST=…`, `Environment=FR_ZEITZONE=…` und `TimeoutStartSec=…` jeweils mit engem Wertmuster
(feste Namensliste `ERLAUBT`, gleich in `units.py` und im Hilfsprogramm; ein neuer Eintrag ist eine Sicherheitsentscheidung des
Product Owners). Alles andere (User, Startbefehle, Rechte, Reihenfolge, Drop-in-Ordner `<einheit>.d`, Timer, nicht
installierte Einheiten) ist gesperrt und braucht einen bewussten Schritt (`einrichten.sh --installieren`).

**Automatisch installieren (Hilfsprogramm mit Root-Rechten).** Hat der Abgleich nur erlaubte Abweichungen, ruft
`veroeffentlichen.sh` `units.py installieren` auf. Das übergibt jede betroffene Einheit samt neuer Datei (stdin) an
`sudo -n /usr/local/sbin/<instanz>-units-installieren <einheit>`, startet danach die Dauerdienste (`rueckmeldungen`,
`konnektor`, `schreiben`, `push`; nie `veroeffentlichen` oder `waechter`) neu und prüft erneut; was dann noch abweicht, wird
einmal gemeldet. Das Hilfsprogramm (Vorlage `betrieb/vorlagen/units-installieren.py`, von `einrichten.sh` mit Instanz und
Benutzer erzeugt) gehört auf dem Server root und liegt außerhalb des Repos, die Software kann es nicht ändern. Es
nimmt nur die sechs Dienst-Einheiten der Instanz an, liest die installierte Datei selbst, ersetzt nur dann, wenn sich beide
Dateien allein in den erlaubten Zeilen unterscheiden (alles andere in gleicher Reihenfolge), verlangt `User=` mit dem
Betriebsbenutzer in beiden, lehnt Fortsetzungszeilen, Steuerzeichen, Nicht-UTF-8, Eingaben über 64 KiB, Symlinks und Drop-ins ab,
ersetzt atomar und führt `systemctl daemon-reload` aus. Es liest weder Umgebung noch Argumente für Pfade oder Programme.
Ausgang 0 installiert, 2 nichts zu tun, 3 abgelehnt. Bekannte, bewusst offene Grenze (Gegenprüfung F101): Die Position der
erlaubten Zeilen zu den übrigen wird nicht verglichen; steht in der Einheit ein `TimeoutSec=`, kann ein verschobenes
`TimeoutStartSec=` den wirksamen Start-Timeout ändern (begrenzt durch das Wertmuster, keine Rechteausweitung). Die Zeilen
werden wie bei systemd nur an Leerzeichen und Tab getrennt; Nicht-ASCII ist nur in Kommentaren und Werten anderer Zeilen möglich.

Einmalig und bewusst (Freigabe des Product Owners, kein Teil des automatischen Laufs): Hilfsprogramm und sudoers-Zeile
installieren, die Befehle nennt `einrichten.sh` am Ende seiner Ausgabe. Ohne installiertes Hilfsprogramm bleibt es bei der
Meldung. Nach einer Änderung der Vorlage `units-installieren.py` muss die Kopie auf dem Server bewusst erneuert werden.

## nginx-Bausteine abgleichen (#206, #445)

Der Konnektor hat drei Drosseln und die Reise-Seiten eine vierte, je Adresse (`betrieb/vorlagen/nginx-zone.conf`, Zonen mit dem Namen der Instanz in einer eigenen
Datei `conf.d/<instanz>-zone.conf`; eine gemeinsam genutzte Datei wie `limit-req.conf` bleibt unberührt, damit keine Namen streiten):
`<instanz>_mcp` großzügig (10 pro Sekunde, burst 40), weil die Claude-App von gemeinsamen Adressen aus aufruft; `<instanz>_anmelden`
streng (5 pro Minute, burst 10); `<instanz>_konto` für Konto, Einladung, Kalender-Abo (30 pro Minute, burst 20); `<instanz>_api` für den Rückmeldedienst der Reise-Seiten (120 pro Minute, burst 10; Zone der Reise-Bausteine, #316; ein Seitenaufruf macht sieben Abfragen, bei 30 pro Minute wurde am 4.11.2026 ein Besucher über fail2ban ausgesperrt).
`/token`, `/register`, die OAuth-Metadaten, Schrift und Symbole haben keine Drossel: Sie kommen von den gemeinsamen Adressen der
Claude-App, ein Limit träfe alle Nutzer zusammen, der Dienst prüft PKCE, Weiterleitungsadressen und Codes selbst.

**Ausnahme für den Server selbst.** Für die Schleife (`127.0.0.1`, `::1`) und `FR_EIGENE_ADRESSEN` ist der Schlüssel der Zonen leer
(`geo` und `map`); nginx rechnet Anfragen mit leerem Schlüssel nicht an. Die Prüfungen des Servers laufen so weiter den echten Weg
über nginx, ohne Kontingent von Besuchern zu verbrauchen. Bedingung: Die Ausnahme ist sicher, solange die Software keine Funktion hat,
mit der der Server eine fremde Adresse aufruft und deren Antwort nach außen weitergibt (heute gibt es keine). Kommt eine solche
Funktion, wird die Ausnahme vorher neu bewertet.

**Abgleich.** Nach jedem grünen Lauf vergleicht `veroeffentlichen.sh` mit `nginx.py pruefen` die erzeugten Bausteine mit den
installierten (`conf.d/<instanz>-zone.conf`, `<instanz>-konnektor-orte.inc`, `<instanz>-konnektor.inc`). Sind die Bausteine noch nicht
eingerichtet, meldet der Abgleich nichts. Ausgang von `nginx.py pruefen`: 0 gleich oder nicht eingerichtet, 3 weicht ab, 1 Fehler.

**Orte-Datei automatisch (#445, Entscheidung des Product Owners vom 9.11.2026).** Weicht ausschließlich die Orte-Datei
`<instanz>-konnektor-orte.inc` ab (neuer Ort, geänderter Burst, Kommentar), ruft `veroeffentlichen.sh` `nginx.py installieren` auf. Das übergibt
das Soll (stdin) an `sudo -n /usr/local/sbin/<instanz>-nginx-orte-installieren` (`FR_SUDO`, `FR_NGINX_HELFER`) und prüft danach erneut.
Ist dann alles gleich, steht nur eine Zeile im Protokoll und der Merker wird gelöscht; sonst kommt die Meldung unten mit der Zeile
`Install attempt: …` (letzte Zeile des Versuchs, etwa `helper missing (<Pfad>)` oder `install skipped: other files differ …`). Endete der Versuch mit einem Fehler, obwohl die Datei danach gleich ist (etwa Neuladen gescheitert), kommt ebenfalls einmal eine Meldung. Ausgang von `nginx.py installieren` wie `pruefen`, 5 wenn
das Hilfsprogramm fehlt oder scheitert (die Meldung nennt dessen Ausgang).

Das Hilfsprogramm (Vorlage `betrieb/vorlagen/nginx-orte-installieren.py`, von `einrichten.sh` mit Instanz, Snippets-Ordner und den drei
Zonen erzeugt) gehört auf dem Server root und liegt außerhalb des Repos, die Software kann es nicht ändern. Es installiert nur genau
diese eine Datei und prüft den ganzen neuen Text gegen eine feste Grammatik (Whitelist): oben nur `location`-Blöcke, Kommentar- und
Leerzeilen; Ortsköpfe `=` und `^~` mit engem Pfadmuster (kein `/` allein, kein `..`, kein `//`; `^~` nur an einer Segmentgrenze, also
mit `/` am Ende oder unter `/.well-known/`; kein Ort überdeckt `/.well-known/acme-challenge`, die Zertifikatsprüfung), Regex `~` nur verankert `^/…$` mit einem Wort oder einer nicht fangenden Gruppe `(?:a|b)?`;
im Block je höchstens einmal `limit_req` mit einer der drei Zonen der Instanz, `limit_req_status 429`, `proxy_buffering off`,
`proxy_read_timeout <Zahl>s` und genau einmal `include <snippets>/<instanz>-konnektor.inc`. Alles andere (`proxy_pass`, `alias`,
`root`, `return`, `add_header`, `if`, `set`, fremde `include`, Variablen, Anführungszeichen, Steuerzeichen, Nicht-ASCII außerhalb von
Kommentarzeilen, verschachtelte Blöcke) lehnt die ganze Eingabe ab. Es liest die installierte Datei selbst (kein Symlink, im Besitz von
root, höchstens 64 KiB), sichert sie nach `/var/lib/<instanz>-nginx-sicherung/` (root, 0700, die letzten 20), ersetzt atomar, prüft mit `nginx -t`,
stellt bei einem Fehler die Sicherung wieder her und lädt nur nach bestandener Prüfung neu. Es liest weder Umgebung noch Argumente
für Pfade oder Programme. Ausgang 0 installiert, 2 nichts zu tun, 3 abgelehnt (nichts verändert), 4 `nginx -t` gescheitert und
zurückgerollt, 5 Neuladen gescheitert (Datei getestet und installiert), 6 Rückweg nicht gesichert (ohne Neuladen). Eine Änderung der
Vorlage, die die Grammatik verletzt, fällt schon im Test der echten Vorlage auf; eine Erweiterung der Grammatik ist eine eigene,
geprüfte Änderung.

Einmalig und bewusst je Instanz (wie bei den Einheiten): Hilfsprogramm nach `/usr/local/sbin/` (root:root, 0755) und die
sudoers-Zeile `<benutzer> ALL=(root) NOPASSWD: /usr/local/sbin/<instanz>-nginx-orte-installieren` installieren; die Befehle nennt
`einrichten.sh` am Ende seiner Ausgabe. Ohne installiertes Hilfsprogramm bleibt es bei der Meldung. Nach einer Änderung der Vorlage
`nginx-orte-installieren.py` muss die Kopie auf dem Server bewusst erneuert werden. Grenze: Auf einem Server mit weiter sudo-Regel
für den Betriebsbenutzer schützt das Hilfsprogramm vor Fehlern (eine falsche Vorlage legt den Webserver nicht lahm), ist aber keine
Grenze gegen einen kompromittierten Betriebsbenutzer.

**Konnektor-Baustein und Zonendatei bleiben Handweg.** Weicht `<instanz>-konnektor.inc` (Weiterleitung, Kopfzeilen) oder
`conf.d/<instanz>-zone.conf` (http-Kontext) ab, steht dort eine fremde Zonendefinition oder fehlt die Orte-Datei, installiert der
automatische Weg nichts. Dann kommt genau eine normale Meldung mit dem einen Befehl zum Beheben, danach erst wieder bei einer anderen
Abweichung (Merker `<FR_DIENST>/nginx-gemeldet`; der Fingerabdruck kommt nur aus der Prüfung nach dem Versuch). Diese beiden Dateien
werden nie automatisch installiert: Ihre Zeilen wirken als Root (ein Ort mit eigener Weiterleitung kann Dateien ausliefern oder, weil
nginx beim Start als Root Logdateien öffnet, schreiben).

Der Befehl aus der Meldung ist `sudo env … nginx.py anwenden` (von Hand, mit Root-Rechten, weil er `/etc/nginx` ändert; der Betriebsbenutzer braucht dafür keine Rechte, `pruefen` liest nur mit `sudo -n cat` unter `/etc/nginx/`, wie bei den Reise-Bausteinen). Er erzeugt das Soll neu, sichert die installierten Dateien in `<FR_DIENST>/nginx-sicherung/<Zeit>/`, installiert alle drei Bausteine, prüft mit `nginx -t` und lädt nur bei bestandener Prüfung neu; besteht sie nicht, stellt er die gesicherten Dateien (und das Fehlen neuer) wieder her und endet mit Fehler; das gilt auch bei einem Abbruch von Hand. Rechte und Besitzer stellt er nicht einzeln wieder her (Zone 644, Bausteine 640, root). `nginx.py anwenden` läuft nie automatisch.

**Hinweis zur Ausnahme:** Die Ausnahme gilt für die Adresse, die nginx sieht (`$remote_addr`). Wird später ein vorgeschalteter Proxy oder CDN verwendet oder `realip` eingeschaltet, erscheint dessen Verkehr als eigene Adresse und wäre unbegrenzt; dann muss die Ausnahme vorher überprüft werden.

**Einmalige Umstellung des Server-Blocks** (bewusst, mit Freigabe des Product Owners): Der Block der Konnektor-Adresse wird auf die Form „fester
Rahmen plus erzeugter Baustein“ gebracht (`include <snippets>/<instanz>-konnektor-orte.inc;` statt der früher im Block selbst geschriebenen Orte), die Zonendatei
kommt nach `conf.d`. Danach gilt der Abgleich. Die Zone `<instanz>_api` der Reise-Bausteine (`nginx-reise.conf`) steht ebenfalls in der eigenen Zonendatei (#316).

**Zone aus einer gemeinsamen Datei umziehen.** Stand die Zone früher in einer gemeinsam genutzten `conf.d/*.conf` (etwa `limit-req.conf`), meldet
`nginx.py pruefen` das als Abweichung (Ausgang 3). `nginx.py anwenden` entfernt dort im selben Lauf genau die Zeile der Instanz samt dem
Kommentarblock direkt darüber, installiert die Zonendatei, sichert beide Dateien (die fremde unter `nginx-sicherung/<Zeit>/fremd/`), prüft
einmal mit `nginx -t` und stellt bei einem Fehler beide wieder her. Das muss ein Lauf sein: nginx verbietet doppelte Zonen, und ohne Definition
laden die Reise-Bausteine nicht. Alle anderen Zeilen und die Rechte der fremden Datei bleiben. Ist die Definition nicht eindeutig (zweimal,
oder weitere Direktiven in derselben Zeile), ändert `anwenden` nichts und endet mit Fehler. Weitere Instanzen brauchen keinen Handschritt.

## Eigener Kartendienst (#444)

Der öffentliche Overpass-Dienst antwortet vom Server aus oft spät oder gar nicht. Eine Instanz kann deshalb für `kartenpunkte_holen` (Konnektor: `map_points_fetch`) einen eigenen Overpass-Dienst betreiben, der nur ihre Regionen enthält, bei Bedarf startet und nach der Ruhezeit wieder endet. Optional: Ohne `FR_KARTENDIENST_REGIONEN` entstehen keine Einheiten, ohne `FR_KARTENDIENST` fragt die Software nur den öffentlichen Dienst (`FR_OVERPASS`).

**Wahl des Dienstes** (`engine/kartendienst.py`): Liegt der Rahmen einer Abfrage ganz in einem Rahmen der Abdeckung (`<FR_KARTENDIENST_ORDNER>/abdeckung.json`, Rand zählt als innen), fragt `overpass_holen` zuerst den eigenen Dienst, höchstens `TEILFRIST_EIGEN` = 10 s und ohne Wiederholung; eine gültige Antwort gilt, auch ohne Treffer. Bei Fehler oder Zeitüberschreitung bekommt der öffentliche Dienst die Restfrist derselben Gesamtfrist (mit seinen bisherigen Regeln). Außerhalb der Abdeckung, über zwei Regionen verteilt oder bei fehlender oder kaputter `abdeckung.json` geht die Abfrage gleich an den öffentlichen Dienst. Die Treffer nennen den antwortenden Dienst und den Stand der Kartendaten (`osm3s.timestamp_osm_base`). Eine Abfrage mit Umkreis (`around`) hat keinen bekannten Rahmen und geht immer an den öffentlichen Dienst.

**Grenze der Abdeckung:** Der Rahmen einer Region ist das Rechteck um ihren Auszug (`osmium fileinfo`), nicht ihre tatsächliche Fläche. Liegt eine Strecke im Rechteck, aber außerhalb der Daten (Meer, Nachbarland), antwortet der eigene Dienst gültig mit null Treffern, ohne Rückfall auf den öffentlichen Dienst. Regionen deshalb kompakt wählen, etwa eine Insel oder ein Land statt eines großen Auszugs, dessen Rechteck viel Fremdes umschließt.

**Einheiten** (`betrieb/vorlagen/kartendienst/`, eigener Unterordner, damit der Abgleich der Einheiten sie nicht sieht; `einrichten.sh` erzeugt sie nach `<EI_ZIEL>/kartendienst/`):
- `<instanz>-kartendienst.socket` lauscht nur auf `127.0.0.1:<FR_KARTENDIENST_PORT>`; der erste Aufruf startet
- `<instanz>-kartendienst-proxy.service` (`systemd-socket-proxyd --exit-idle-time=<FR_KARTENDIENST_RUHE>`), gebunden an
- `<instanz>-kartendienst.service`: `docker run --rm` mit dem Image per Digest, Speichergrenze, `StopWhenUnneeded=yes`; bereit erst nach einer echten Mini-Abfrage (`ExecStartPost`; der Statusaufruf des Images antwortet mit 502). Endet der Proxy, endet der Container. Container und Einspielen laufen mit `OVERPASS_USE_AREAS=false`: Die Software stellt nur Abfragen mit Rahmen und braucht keine Flächen; ohne deren Erzeugung und Dauerschleife spart der Dienst Speicher und Dauerlast.
- `<instanz>-kartendienst-aktualisieren.service` und `.timer`: täglich nachts `kartendienst.sh aktualisieren`.

**Einspielen** (`betrieb/kartendienst.sh einspielen`, als Dienstbenutzer in der Gruppe `docker`): prüft freien Speicher (rund 1,6 GiB je kleiner Region) und Platz (etwa 2 GB), wartet auf einen laufenden Lauf des Veröffentlichens (dessen Sperre) und läuft nie doppelt. Es lädt die Auszüge der Regionen von Geofabrik mit Prüfsumme (die Adresse steht in `engine/kartendienst.py`), verbindet sie im Container mit osmium zu `osm.bz2` und spielt sie im Modus `init` in einen Nebenordner ein (Rechte 755). Nach einer erfolgreichen Probeabfrage gegen den Nebenordner schreibt es `abdeckung.json` (`stand` = Zeitpunkt des Einspielens, `daten` = Stand der Daten, `regionen_pruefsumme`, `rahmen` je Region aus `osmium fileinfo`) und schaltet durch Umbenennen um; der alte Stand bleibt bis dahin liegen. Scheitert ein Schritt, bleibt der bisherige Stand unverändert. `aktualisieren` spielt nur ein, wenn `abdeckung.json` fehlt, älter als ein Monat ist oder die Prüfsumme der Regionenliste abweicht.

**Einrichten:** Regionen, Ordner und `FR_KARTENDIENST` in die Einstellungen der Instanz, dann nennt `einrichten.sh` die einmaligen Befehle: Datenordner mit Rechten 755 anlegen (sein Elternordner gehört dem Dienstbenutzer), Dienstbenutzer in die Gruppe `docker`, Einheiten installieren, erstes Einspielen, Socket und Timer aktivieren. Abschalten ohne Neuaufbau: `FR_KARTENDIENST` leeren, dann gilt ab dem nächsten Aufruf nur der öffentliche Dienst; `systemctl disable --now <instanz>-kartendienst.socket` legt die Einheiten still.

**Überwachung:** kein eigener Heartbeat; der Monitor der Instanz prüft als Teil-Check das Alter von `abdeckung.json` (Warnung ab 40 Tagen).

**Lizenzen:** Overpass API steht unter der AGPL; das Image `wiktorn/overpass-api` wird nicht mitgeliefert, sondern beim Betrieb geladen und per Digest gepinnt (`KD_BILD` in `betrieb/gemeinsam.sh`; ein neuer Digest ist eine bewusste Änderung). Die Daten stammen aus OpenStreetMap (© OpenStreetMap-Mitwirkende, ODbL); die Namensnennung steht in jedem Treffer.

## Umzug auf den Software-Klon (#454)

Eine Instanz der alten Anordnung (Reisen-Repo mit Submodul `frieda/` als Bauordner) zieht ohne Handschritt um (#250): Der letzte Software-Stand, der noch über das Submodul kommt, führt nach jedem grünen Lauf von `veroeffentlichen.sh` den Umzug aus, Schritt für Schritt, jeder wiederholbar:

1. **Software-Klon** `<FR_SEITEN>/_software` anlegen oder holen (öffentlich, ohne Anmeldung, nur `main`), auf genau den Commit des Submoduls, mit dem der Lauf grün war.
2. **Einstellungen, Meldeweg, Prüfungen** nach `<FR_DIENST>/instanz/` kopieren (`einstellungen.env`, `melden.sh`, optional `tests/`), nur wenn das Ziel fehlt oder älter ist; Neueres am Ziel wird nie überschrieben.
3. **Python-Umgebung** unter `<FR_DIENST>/python` bauen und den Klon prüfen (Nachweis der Pflichtprüfungen oder Tests im Klon). Sind 1 und 3 für einen Commit des Submoduls grün, steht er in `<FR_DIENST>/umzug-454.geprueft`; spätere Läufe wiederholen sie für denselben Commit nicht und gehen gleich zu Schritt 4 (Schritt 2 läuft jedes Mal, er überschreibt nie Neueres).
4. **Erst wenn 1 bis 3 grün sind:** die Units auf den Klon abgleichen (`FR_WURZEL`, Skripte unter `__SOFTWARE__/betrieb/…`, Python unter `<FR_DIENST>/python`; über das Root-Hilfsprogramm wie beim Abgleich der Einheiten). Das ist der letzte Schritt. Meldet der Abgleich gesperrte Abweichungen (neue Pfade in `ExecStart` und `FR_WURZEL` stehen nicht in der Erlaubnisliste, Abschnitt „Einheiten abgleichen“), endet der Umzug hier, bis die Erlaubnisliste das zulässt oder die Units bewusst mit `einrichten.sh --installieren` aus dem Klon installiert sind. Die Warnzeile dazu steht einmal je Commit und Befund im Protokoll (`<FR_DIENST>/umzug-454.units`), nicht in jedem Takt.

`__SOFTWARE__` in den Vorlagen ist der Ordner, aus dem `betrieb/` kommt: in der alten Anordnung `<FR_WURZEL>/frieda`, im Klon `FR_WURZEL` selbst; `FR_DIENST` steht nur im Klon als Umgebungswert in den Units (dort liegen die Einstellungen unter `<FR_DIENST>/instanz/`). So gleichen die Soll-Units der alten Anordnung den heute installierten, und der Abgleich meldet bis zum Umzug nichts.
5. Zustand `<FR_DIENST>/umzug-454` auf `fertig`; der Lauf startet sich aus dem Klon neu (`exec`).

Scheitert ein Schritt vor 4, bleibt alles beim alten Weg: eine Warnzeile „move (#454)“ im Protokoll, kein Alarm, der nächste Lauf (alle 5 Minuten) versucht denselben Umzug erneut. Ein Lauf des alten Skripts nach dem Umzug macht im Klon weiter.

**Vorbedingung (Infrastruktur):** Zwei Stellen außerhalb dieses Repos hängen am Pfad des alten Bauordners und müssen beide Anordnungen kennen, bevor der Umzug auf eine Instanz kommt; sonst wird er nicht ausgeliefert (Auslieferungstor, Issue im Infrastruktur-Repo, verlinkt in #454):

- **Monitor** (`monitor.sh` der Infrastruktur): Der Rückstands-Check liest heute `.git/modules/frieda/HEAD` des alten Bauordners. Künftig vergleicht er `HEAD` des Software-Klons mit `main` der Software (Warnung ab etwa 6 h), ohne Klon den alten Ort.
- **Backup:** Der Aufruf von `sichern.sh` im Server-Backup muss den neuen Pfad `<FR_SEITEN>/_software/betrieb/sichern.sh` finden (statt `<Bauordner>/frieda/betrieb/sichern.sh`), sonst entsteht eine Sicherung ohne frischen Schnappschuss. `<FR_DIENST>/instanz/` liegt im gesicherten Bereich.

**Rückweg:** Der alte Bauordner und seine Vorlagen bleiben unangetastet. Zurück geht es mit demselben Mechanismus: `<FR_DIENST>/umzug-454` auf `alt` setzen (dann zieht kein Lauf erneut um) und die Units auf den alten Bauordner abgleichen (`FR_WURZEL=<alter Bauordner> <alter Bauordner>/frieda/betrieb/units.py pruefen` und `installieren`); Veröffentlichen, Wächter, Schreibweg und Kartendienst laufen dann wie vorher. Kein eigener Befehl.

**Rückbau** des Git-Wegs (`schreiben_git.py`, `stand_git.py`, `vergleichslauf.sh`, Arbeitskopien `_bau-schreiben-*`, Workflow „Software nachziehen“, Archivierung des Reisen-Repos, Entfernen des alten Bauordners) ist ein eigenes Folge-Issue nach einer Beobachtungszeit.

## Bauordner und Arbeitsordner

Der **Bauordner** ist der Software-Klon `<FR_SEITEN>/_software` (#454; vor dem Umzug ein Klon des Reisen-Repos) und spiegelt nur `main`. Timer, Schreibweg und Wächter laufen von dort, ihre Units nennen ihn mit `FR_WURZEL`. Von Hand wird darin nichts geändert, kein Branch ausgecheckt und nichts committet. Sonst setzt das Veröffentlichen aus (es überspringt jeden Lauf, solange der Ordner nicht auf `main` oder nicht sauber ist). `deploy.sh` und `veroeffentlichen.sh` laufen nur mit `FR_WURZEL`. `deploy.sh` baut außerdem nur, wenn der Ordner auf dem Branch `main` steht. Ein Aufruf aus einem anderen Klon bricht damit ab, statt von dort zu veröffentlichen (#137). Was nicht im Repo liegt, liegt daneben: die Python-Umgebung unter `<FR_DIENST>/python` (vor dem Umzug `engine/.venv` im Bauordner), die Werkzeuge (`engine/.bin`) und die Grundkarten. Für automatische Karten holt `veroeffentlichen.sh` die Grundkarte vor dem Bau selbst, wenn sich ihr Rahmen geändert hat (`werkzeuge/grundkarte_auto.py`, `FR_GRUNDKARTE_AUTO`, Epic #225; ohne Netz baut die Reise trotzdem). Eine neue Grundkarte einer handgepflegten Karte kommt mit `FR_WURZEL=<Bauordner> frieda/werkzeuge/karte-holen.sh <reise>` direkt dorthin (ignorierte Dateien, `main` bleibt sauber), danach `FR_WURZEL=<Bauordner> frieda/betrieb/veroeffentlichen.sh --immer`.

Gearbeitet wird in einem eigenen **Arbeitsordner**, einem normalen Klon mit eigener Python-Umgebung und Branches. Er wird über Pull Requests nach `main` gebracht, danach holt der Timer den Stand in den Bauordner. Die Software selbst wird nur in ihrem eigenen Repo geändert. Im Reisen-Repo ändert sich das Submodul `frieda/` nur durch einen Versionswechsel (Workflow „Software nachziehen“).

## Zurückrollen und sperren

- **Seite:** den schlechten Stand auf `main` mit `git revert <commit>` zurücknehmen (in einem Arbeitsordner, über einen PR). Der Timer veröffentlicht den neuen Stand, der Service Worker bietet den alten Inhalt als neue Version an. Im Bauordner wird nichts ausgecheckt.
- **Dienste:** der Code liegt in `<FR_DIENST>/`. Ein Revert der Software (neuer Stand des Submoduls auf `main`) bringt den alten Code beim nächsten Veröffentlichen zurück.
- **Zugang sperren:** Person mit `person_entfernen` aus der Reise nehmen oder das Konto sperren (`konten.py`); der Link zur Seite wird gesperrt, indem man den Token im nginx-Baustein ändert.
